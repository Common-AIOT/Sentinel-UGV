# Streaming PoC — 설계 기록과 실측

이 디렉터리는 **기록과 측정 도구**만 담습니다. 실제 구현은 ROS 2 패키지에 있습니다.

| 위치 | 성격 |
|---|---|
| `jetson/streaming_poc/` (여기) | 확정 계약, PoC-A/B 실측 기준선, 측정 스크립트 |
| [`jetson/ros2_ws/src/sentinel_streaming/`](../ros2_ws/src/sentinel_streaming/) | 실행되는 노드·launch·설정 (S15P11A301-106) |

카메라를 한 번만 열어 AI와 스트리밍 소비자에게 프레임을 분배하고, 로컬 우선 WebRTC 스트림을 제공합니다. 이벤트 녹화는 전 5초·후 10초 링 버퍼를 기본값으로 사용합니다.

이 문서는 S15P11A301-62(영상 파이프라인 설계)의 확정 계약과 PoC 합격 기준을 담는다. 구현은 후속 티켓으로 분리한다.

## 파이프라인 구조 (확정)

```text
Brio 100 (MJPEG 1280x720@30)
  -> usb_cam(raw_mjpeg, 카메라 단독 점유)
  -> /camera/image_raw/compressed  (sensor_msgs/CompressedImage, jpeg)
       |
       +-- 스트리밍/녹화 노드 : nvv4l2decoder(mjpeg=1) -> nvvidconv -> x264enc(1회) -> h264parse -> tee
       |        +-- MediaMTX(RTSP) -> WebRTC
       |        +-- segment writer(1초 MPEG-TS 링 버퍼)
       +-- AI 노드           : nvv4l2decoder(mjpeg=1, 독립) -> TensorRT -> 탐지 결과만 발행
```

Orin Nano에는 HW H.264 인코더(NVENC)가 없다(`nvv4l2h264enc` 미등록 확인). 따라서 x264enc(CPU) 소프트웨어 인코딩을 사용한다. 이는 선택이 아니라 하드웨어 제약이며, 기존 명세의 "Jetson H.264 HW 인코더" 전제는 폐기한다.

## 카메라 메시지 계약 (확정)

```text
topic      : /camera/image_raw/compressed
type       : sensor_msgs/msg/CompressedImage
format     : jpeg
resolution : 1280 x 720
framerate  : 30 FPS (실측 목표 29~30)
frame_id   : camera_optical_frame
header.stamp : V4L2 캡처 시각
```

- `/camera/image_raw`(RGB)는 발행하지 않는다. 720p RGB 30 FPS를 DDS로 뿌리면 약 83MB/s로 불필요한 부하가 생긴다.
- `frame_id`는 드라이버 설정(`config/brio_100.yaml`)에서 `camera_optical_frame`으로 발행한다. 과거 `camera_frame` 값과의 불일치는 62에서 정정 완료.
- TF: `camera_link -> camera_optical_frame`은 로봇 URDF(`sentinel_description`, S15P11A301-74)의 `robot_state_publisher`가 발행한다(REP-103 optical 회전, quaternion `(-0.5, 0.5, -0.5, 0.5)`). `camera_link` 자체는 짐벌 dynamic TF로 `gimbal_pitch_link`의 자식(후속 구현).

## 타임스탬프 / PTS 계약 (확정)

- 저장·발행 시 3종 시각을 함께 기록한다: 스트림 PTS, monotonic time, wall time.
- ROS `header.stamp`(V4L2 캡처 시각) -> GStreamer PTS 변환 규칙:
  ```text
  첫 프레임 PTS = 0
  이후 PTS      = 현재 header.stamp - 첫 header.stamp
  ```
- **카메라 재시작 / PTS 리베이스 시**: 리베이스는 반드시 **새 세그먼트 경계를 강제**한다. 진행 중이던 TS/MP4 조각을 즉시 finalize하고 다음 IDR부터 새 조각을 연다. muxer가 시간 불연속(discontinuity)을 조각 경계로만 겪게 하여 재생 호환성 문제를 막는다.
- 이벤트와 영상 조각 매칭은 wall time 기준으로 하되, 조각 내부 상대 위치는 PTS로 계산한다.

## PoC 합격 기준 (62 범위)

### PoC-A. HW MJPEG 디코딩 검증

HW 디코딩 엘리먼트는 **`nvv4l2decoder mjpeg=1`을 사용한다. `nvjpegdec`는 사용 금지.**

| 디코더 | 실측 FPS | 판정 |
|---|---|---|
| (디코더 없음, 카메라 전달만) | 30.0 | 카메라 정상 기준선 |
| `nvjpegdec` | **5.09** | 기각 — 엘리먼트 결함, 약 196ms/frame으로 파이프라인 전체를 5FPS로 제한 |
| `nvv4l2decoder mjpeg=1` | 30.0 | **채택** |
| `jpegdec` (SW) | 29.9 | 폴백 경로로 검증됨 |

- [x] 디코더별 단기 FPS 비교 (위 표)
- [x] `jpegdec`(SW) 폴백 경로 동작 확인
- [x] `nvv4l2decoder mjpeg=1`로 10분(18000프레임) 연속 디코딩
- [x] NVJPG 엔진 `runtime_status: active` 확인(CPU 폴백 아님을 검증)
- [x] 출력 FPS·CPU·메모리·온도 기록
- [x] 연속 decode error·프레임 정지 없음

합격: 평균 29 FPS 이상 / 10분 무중단 / 연속 decode error 없음 / NVJPG HW 경유 확인.

**2026-07-24 10분 연속 실측 — 합격**:

```text
런타임      : 602초 완주, exit 0, 프레임 드롭 0, decode error 0
FPS         : 평균 29.93 (순간값 1167샘플: 최소 29.69, 29 미만 0건)
NVJPG       : 전 구간 active (10초 간격 60회 샘플, 엔진 2개 모두)
CPU         : 코어당 2~5% @ 729MHz(최저 클럭 유지) — 헤드룸 매우 큼
온도/메모리 : tj 최대 46°C, RAM 최대 2921MB(증가 추세 없음), 보드 약 3.9W
```

**측정 범위와 한계**: 위 수치는 **디코더 단일 인스턴스 + 디코드 전용 파이프라인**에서 나온 값이다. CPU 2~5%는 729MHz 최저 클럭이 유지된 상태의 값이므로, x264 인코딩·TensorRT 전처리·DDS 직렬화가 붙은 뒤의 값이 아니다. 따라서 이 결과로 확정된 것은 **"MJPEG 디코딩 자체는 병목이 아니다"**까지이며, "독립 디코딩 2회" 구조의 부하는 PoC-B에서 2인스턴스 동시로 측정해야 확정된다. NVJPG 엔진 하나를 두 인스턴스가 공유하므로(720p30 × 2 = 60fps 상당) 용량 여유는 실측 대상이다.

남은 검증은 PoC-B(x264 인코딩 + 동시부하 헤드룸)로 넘어간다.

### PoC-B. x264 성능 + 풀부하 헤드룸 — **게이트**

PoC-B는 형식적 단계가 아니라 **구현 착수 게이트**다. 아래 합격 조건을 통과하지 못하면 비트레이트·해상도·AI 추론 FPS를 조정한 뒤 재측정하고, 조정값을 32장에 반영한다.

```text
Brio MJPEG -> nvv4l2decoder(mjpeg=1) -> nvvidconv -> I420 -> x264enc -> h264parse -> fakesink/file
x264 설정: ultrafast + zerolatency, 2~3 Mbps, key-int-max=30, bframes=0, closed GOP, baseline, alignment=au
```

**측정 조건 (모두 동시에 걸린 상태)**: 카메라 + HW MJPEG 디코딩 **2인스턴스**(스트리밍 + AI) + x264enc + LiDAR `/scan` + YOLO 상당 GPU/CPU 점유.

측정 스크립트는 [`poc/`](poc/)에 있다. 결과는 그 스크립트로만 만든다.

인코딩·부하:

- [x] 720p30 유지, `ffprobe`로 H.264 결과 검증(profile=baseline, bframes=0, GOP 30)
- [x] CPU 부하 기록 (Orin Nano 6코어 기준)
- [x] 디코더 2인스턴스 동시 시 출력 FPS 기록 (단일 인스턴스 대비 열화 확인)
- [x] YOLO 몫으로 남는 CPU 헤드룸 잔량 명시 — 3차 측정에서 YOLO26n FP16 15 FPS 부하를 걸고 loadavg 최대 2.63/6코어 확인

DDS 전송 경로:

- [x] `/camera/image_raw/compressed` 구독자 2개 동시 상태에서 구독자별 수신 FPS·드롭 계수 기록
- [x] JPEG 프레임 크기 **평균·최대** 측정(씬 복잡도 변화 포함) — 정적 31KB, 고복잡도 평균 110KB / 최대 128KB. 후자에서 전 프레임 단편화 상태로 10분 손실 0
- [x] SHM 전송 정상 동작 확인 — 이번 측정에서 `open_and_lock_file failed` 0건. 우회 설정 불필요
- [x] QoS 확정: 발행자는 `RELIABLE`/`VOLATILE`, 구독자가 이를 일치시킨다

저장·시각:

- [ ] 링 버퍼 상시 쓰기(약 1.1GB/h) 상태에서 쓰기 지연 스파이크와 non-leaky 녹화 큐 영향 측정. **현재 저장 매체는 microSD이며 NVMe가 아니다**(32-5 「저장 매체」)
- [ ] 카메라 노드 기동 전/후 시각 동기 점프 시나리오에서 `header.stamp`와 wall clock 정합성 확인 (`usb_cam`의 epoch 오프셋은 기동 시 1회 고정)

**합격 조건**:

```text
1. x264 인코딩 실측 FPS >= 29 (720p, 위 동시 조건 하에서)
2. 압축 토픽 구독자 2개 모두 프레임 드롭 0
3. H.264 조건 충족 (baseline, bframes=0, GOP 30)
4. JPEG 최대 크기가 DDS 단편화 손실을 유발하지 않음
5. YOLO 몫 CPU 헤드룸이 정량적으로 남아 있음
6. 링 버퍼 쓰기 지연으로 인한 조각 누락 0
```

**게이트를 통과하지 못한 이유 4가지**:

1. **조건 2 미달** — 1회차에서 `ai` 구독자만 236ms(약 7 프레임 주기) gap 1회, 6프레임 유실. 같은 순간 `streaming` 구독자는 0이었다. 2회차에서는 재현되지 않았다. 재현되지 않는다는 것이 안전하다는 뜻은 아니다. 구독자 하나만 유실된 것은 DDS 수신 경합 또는 스케줄링 지연을 시사하며, 원인을 규명하지 않은 채 넘기면 운영 중 간헐적 프레임 손실로 남는다. 장시간(10분 이상) 반복 측정과 `depth`·실행 우선순위 조정 실험이 필요하다.
2. **조건 4는 정적 장면에서만 성립** — 측정된 JPEG 최대는 32~35KB인데 S15P11A301-66 당시에는 평균 약 105KB였다. Fast DDS 단편화 임계(약 64KB)가 이 두 값 사이에 있다. 즉 **장면이 복잡해지면 단편화가 시작되고 조건 2의 결과도 달라진다.** 움직임·질감이 많은 장면으로 재측정해야 한다.
3. **조건 5는 부분 측정** — YOLO 상당 GPU/CPU 부하를 실제로 걸지 않았다. loadavg 1.67~2.04는 그 부하가 없는 상태의 값이므로 **헤드룸의 상한**이다.
4. **조건 6은 측정 불가** — 링 writer가 없다. S15P11A301-106에서 구현 후 측정한다.

600초 연속. 1차와 달리 카메라가 본 장면이 고복잡도여서 JPEG가 100KB 규모로 커졌다. 조건 4를 판정하려던 바로 그 조건이 우연히 성립했다.

**조건 2 합격.** 17958프레임 × 구독자 2개, 10분간 드롭 0·gap 0. 1차의 6프레임 유실은 90초 구간의 일시적 현상이었고 10분 측정에서 재현되지 않았다.

**조건 4 합격, 그리고 근거가 1차보다 강하다.** 전 프레임이 Fast DDS UDP 페이로드 한계(약 64KB)를 넘어 **항상 단편화되는 상태**에서 10분간 손실이 0이었다. `RELIABLE` QoS가 단편 유실을 재전송으로 덮는다. 최대 간격도 정상 프레임 주기와 같아 지연 스파이크도 없었다. 즉 **100KB급 프레임은 안전하다** — 우려했던 단편화 손실은 `RELIABLE`에서 발생하지 않는다.

**남은 미통과 사유 3개**:

1. **조건 5 미측정** — YOLO 부하가 시작 직후 죽었다. `NVML_SUCCESS == r INTERNAL ASSERT FAILED at c10/cuda/CUDACachingAllocator.cpp:1131`. PyTorch 캐싱 할당자가 메모리 압박에서 재시도할 때 NVML로 가용량을 조회하는데 Tegra 통합 GPU는 NVML을 지원하지 않아 assert로 터진다. 단독 실행(15 FPS, FP16)은 정상이었으므로 원인은 동시 부하 상태의 메모리 부족이다. 상세와 대응은 [`poc/README.md`](poc/README.md)의 「메모리 제약」 참조.
2. **조건 1의 소스가 저복잡도** — 인코딩 브랜치는 1차에서 캡처한 정적 장면 MJPEG 샘플을 입력으로 썼다. 반면 DDS 측정은 실시간 고복잡도 장면을 봤다. x264 부하도 장면 복잡도에 비례하므로, **조건 1의 30.027 fps는 저복잡도 소스 기준**이다. 고복잡도 샘플로 재캡처해 재측정해야 완전히 일관된 값이 된다.
3. **조건 6 측정 불가** — 링 writer가 없다. S15P11A301-106에서 구현 후 측정한다.

**다음 조치**: 고복잡도 장면으로 MJPEG 샘플을 재캡처해 조건 1을 같은 조건에서 재측정한다. YOLO 부하는 메모리 여유를 확보한 상태(IDE 등 미실행)에서 재시도하고, 재발하면 `imgsz`를 512/416으로 낮춘다. 두 항목이 정리되면 조건 6만 남아 106으로 이관된다.

#### 2026-07-27 3차 측정 (10분, 고복잡도, YOLO 부하 포함) — **측정 가능 범위 전부 합격**

IDE를 종료해 메모리 여유를 확보하고(available 5859MB) 고복잡도 샘플(프레임 평균 127KB, JPEG 879프레임)로 재측정했다. `poc/poc_b_run_all.sh`로 캡처부터 정리까지 단일 실행했다.

| 조건 | 실측 | 판정 |
|---|---|---|
| 1. 인코딩 FPS ≥ 29 | 18012프레임 / 600초 = **30.020 fps**, 최저 순간 29.935 | **합격** |
| 2. 구독자 2개 드롭 0 | 각 17958프레임 29.93 fps, 드롭 0, gap 0회, 최대 간격 0.0361s | **합격** |
| 3. H.264 조건 | Constrained Baseline, b-frame 0, GOP 30, 1280×720 | **합격** |
| 4. JPEG 최대 < 손실 유발 | 평균 110236B / 최대 **128479B**, 전 17958프레임 64KB 초과, 손실 0 | **합격** |
| 5. YOLO 몫 CPU 헤드룸 | 추론 9000회 **15.0 FPS 정확 달성**, 밀림 0회. loadavg 중앙 1.91 / 최대 2.63 (6코어 = 32~44%) | **합격** |
| 6. 링 버퍼 조각 누락 | 링 writer 부재로 측정 불가 | **106으로 이관** |

```text
인코딩 소스  : 고복잡도 MJPEG 샘플 (프레임 평균 127KB) — 조건 4와 동일 기준
AI 디코더    : 최저 순간 29.833 fps (2번째 독립 인스턴스)
YOLO 추론    : FP16 imgsz=640, 지연 평균 47.51ms / p95 51.24ms / 최대 62.8ms
자원         : loadavg 최대 2.63/6코어, 메모리 최대 3022MB/7619MB, tj 최대 49.7°C
```

**조건 1의 소스 일관성 문제가 해소됐다.** 2차에서는 인코딩 브랜치가 정적 장면 샘플을 봤지만, 3차는 프레임 평균 127KB의 고복잡도 샘플이다. 즉 x264도 DDS와 같은 복잡도의 입력을 처리한 상태에서 30.020 fps를 유지했다.

**조건 5 합격의 성격**: PyTorch(TensorRT 미변환) 추론을 부하로 걸었으므로 실제 운용보다 CPU 부하가 크다. 즉 이 결과는 **하한 보장**이다. TensorRT 전환 후에는 헤드룸이 더 늘어난다. 목표 15 FPS를 밀림 0회로 정확히 달성하면서 6코어 중 최대 44%만 썼고, 메모리도 60% 남았다.

**2차의 NVML assert 원인이 확인됐다.** 3차는 IDE 종료로 available 메모리가 5859MB였고 실패가 재현되지 않았다. 2차 실패는 VS Code 서버가 점유한 약 2.7GB 때문이었다. 실제 로봇 운용에는 없는 부하다.

**게이트 판정**: 측정 가능한 5개 조건 전부 합격. 조건 6은 링 writer가 구현 범위(S15P11A301-106)에 있어 62 시점에 측정할 수 없으므로, **106의 착수 조건이 아니라 106 내부의 검증 항목으로 이관**한다. 이로써 62의 PoC 게이트는 통과로 판정한다.

측정 중 캡처 단계에서 `/dev/video0 점유 중` 경고가 출력됐으나 샘플은 879프레임·평균 127KB로 정상 생성됐다. 스크립트의 잔여 프로세스 처리 경로에 결함이 있는 것으로 보이며 측정 결과에는 영향이 없다. `poc_b_capture.sh`에서 잔여 카메라 점유 프로세스를 정리하도록 보완했다.

## 장애 격리 원칙

```text
카메라 노드 종료   -> 전체 영상 중단, CAMERA_FAULT
스트리밍 노드 종료 -> AI 계속 동작
MediaMTX 종료      -> AI·녹화 계속 동작
AI 노드 종료       -> 관제·녹화 계속 동작
네트워크 단절      -> 로컬 AI·녹화 계속 동작
녹화 실패          -> 관제·AI 유지, 오류 보고
```

스트리밍 큐만 bounded/leaky, 녹화 큐는 non-leaky. MediaMTX 장애가 녹화를 막지 않도록 tee 출력에 독립 큐를 둔다.
