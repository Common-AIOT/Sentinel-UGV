## 0. 왜 로컬을 먼저 끝내는가

젯슨에서 실패하면 **원인이 코드인지 환경인지 구분이 안 된다.** 젯슨에는 변수가 많다 —
시계 리셋, CPU int8, 블루투스 A2DP 지연, 8GB 메모리.

실제로 그렇게 헤맸다. **165의 시나리오 C가 3차까지 재현에 실패**했는데, 원인은 코드가
아니라 블루투스 A2DP의 100~250ms 싱크 버퍼였다. 재생이 끝났다고 판단한 뒤에도 스피커에서
안내 음성 꼬리가 나오고 있었고 그 순간 녹음이 시작됐다. 165 티켓 자체가 **"유선 출력으로
A2DP 지연을 변수에서 제거하는 것이 원인 규명에 유리하다"** 고 적어 두었다.

그래서 순서는 이렇다.

| | 어디서 | 무엇을 판정 |
|---|---|---|
| 1 | **로컬 PC (유선 출력)** | 코드가 맞게 동작하는가 |
| 2 | **젯슨** | 실기에서도 되는가 · RAM · 지연 · 최종 인수 |

RAM·STT 지연·최종 인수는 **로컬 값으로 대체할 수 없다**(`measurements/메모리-예산.md` 부록 A).


시나리오마다 로그를 따로 남긴다.

| 시나리오 | 무엇을 하는가 | 합격 |
|---|---|---|
| **A 중증** | `네, 들려요` → `숨쉬기가 좀 힘들어요` → `다리가 눌려서 못 움직여요` → `저랑 아저씨 한 분, 두 명이요` | `riskLevel=IMMEDIATE` · 긴급 `YES` · 인원 `2` |
| **B 경상** | `네, 들립니다` → `아니요, 괜찮습니다. 다친 데 없어요` → `네, 걸을 수 있어요` → `저 혼자예요` | `riskLevel=DELAYED` · 이동 `YES` · 긴급 `NO` |
| **C 완전 무응답** ⭐ | INTRO에서 5초 침묵 → 재질문 재생 → 다시 침묵 → 끝까지 침묵 | `[NOVOICE]` 2회 · 재질문 WAV 재생 · `anyResponseDetected=false` · `riskLevel=IMMEDIATE` |
| **D STT 실패** ⭐ | INTRO에서 **말이 아닌 소리** 5초(신음·웅얼거림·숨 몰아쉬기) | `[STTFAIL]` · **`anyResponseDetected=true`** · `operatorReviewRequired=true` |
| **E 혼합** | A로 시작해 중간에 침묵으로 전환 | 부분 수집 값이 보존됨 |

**C와 D가 이번 검증의 핵심이다.**

- **C**는 165가 3차까지 재현 실패한 그 경로다. `[STTFAIL]`로 분류되면 여전히 에코가 유효
  발화로 통과하는 것이다. 1차 방어선은 `LISTEN_DELAY`(기본 0.3초), 2차는 문구 대조
  에코 가드다. 실패하면 지연을 올려 본다.

  ```bash
  set SENTINEL_LISTEN_DELAY=0.6
  ```

- **D에서 `anyResponseDetected=false`가 나오면 명세 33-3 위반이며 즉시 보고할 결함이다.**
  음성은 감지됐고 STT만 실패한 것이므로 무응답·의식없음으로 기록해선 안 된다.

결과는 `%USERPROFILE%\sessions\<세션>\report.json`과 `session.jsonl`에 남는다.
`session.jsonl`의 `sttText`와 `extraction`을 나란히 보면 원인이 STT인지 추출인지 갈린다.
각 턴의 `recordMs`, `vadMs`, `sttMs`, `gmsMs`, `turnMs`는 Jetson 원격 ASR
실기에서 단계별 지연을 구분하는 값이다. `safetyReason`이
`MOBILITY_YES_NEGATION_CONFLICT`이면 부정 흔적과 이동 가능 YES가 충돌해 최종값을
`UNKNOWN`으로 강등한 것이다.

### 3-00. 마이크가 실제 마이크인지 — 가장 먼저

**2026-08-04에 이걸 안 보고 리허설 영상 295초를 빈 단자로 녹음했다**(S15P11A301-257,

`sudo` 붙이지 않는다. 젯슨 화면에 로그인한 사용자로 실행한다 — PulseAudio는 사용자마다
따로 돌기 때문에 `sudo`면 엉뚱한 답이 나온다.

```bash
pactl info | grep -i "default source"; pactl list sources | grep -E "Name:|Mute:|State:"
```

**기본 소스가 `platform-sound`나 `.monitor`로 끝나면 틀렸다.** BRIO로 바꾼다.

```bash
pactl set-default-source $(pactl list sources short | grep -i brio | awk '{print $2}')
```

바꾼 뒤 실제로 소리가 잡히는지 본다. 5초 동안 아무 말이나 한다.

```bash
arecord -d 5 -f S16_LE -r 48000 -c 1 /tmp/mictest.wav; python3 -c "import wave,audioop; w=wave.open('/tmp/mictest.wav'); print('peak =', audioop.max(w.readframes(w.getnframes()), 2))"
```

**통과 기준** — `peak`가 0이 아니다(2026-08-04 정상값 2913). **0이면 여기서 멈춘다.**

> 스택이 이미 돌고 있으면 기본값만 바꿔도 `pulsesrc`는 갈아타지 않는다. 스택을 재시작한다.
> 누가 붙잡고 있는지는 `pactl list source-outputs | grep -E "Source:|application.name"`.

## 6. 미리 알아둘 함정

| 함정 | 증상 | 대응 |
|---|---|---|
| **기본 입력이 빈 단자** | **오류 없이 녹음이 전부 peak 0** | **§3-00을 먼저 한다.** 실제로 리허설 295초를 잃었다(§9-8) |
| `--input-match "BRIO"`가 젯슨에서 실패 | 장치 목록에 BRIO가 없음 | 정상이다 — PulseAudio가 카드를 독점해 PortAudio가 못 본다. `pulse`를 쓴다 |
| 젯슨 시계 리셋 | GMS 401, pip 인증 오류 | 3-0의 `date -s` |
| 원격 ASR 연결 실패 | timeout/refused/unauthorized | GPU health·바인딩·방화벽·API 키 확인 |
| 성능 모드 초기화 | 지연이 이유 없이 나쁨 | 세션마다 `nvpmodel -m 0` |
| 블루투스 HFP로 잡힘 | 음질 붕괴 | Active Profile을 `a2dp-sink`로 |
| A2DP 꼬리 재생 | 시나리오 C가 `[STTFAIL]`로 | 유선으로 먼저 · `SENTINEL_LISTEN_DELAY` 상향 |
| 정확도가 shadow 벤치보다 나쁨 | — | Jetson 실기 음원·소음 조건으로 원격 ASR을 재측정한다 |
| CER만 보고 판단 | 위험이 안 보임 | 슬롯 정확도를 함께 본다 |
