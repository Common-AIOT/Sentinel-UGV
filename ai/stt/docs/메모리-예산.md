## 1. 한눈에 보는 결론

**Jetson Orin Nano 8GB에서 음성 파이프라인 단독 실측 결과:**

| 핵심 수치 | 값 |
|---|---|
| 보고 순간 피크 RAM | **5.62GB / 7.4GB** |
| 남는 여유 | **~1.9GB** |

**팀에 공유할 결론:**

1. Orin Nano의 8GB는 **CPU·GPU 통합 메모리**다. 로컬 LLM(qwen2.5:3b) 포함 피크가 5.62GB로, **비전(YOLO)·SLAM·Nav2 몫이 ~1.9GB뿐**이라 통합 시 부족할 가능성이 높았다.
2. **배포 리스크 발견:** qwen2.5:3b는 여유 RAM이 있어 보여도 **page cache가 차 있으면 GPU 로드 실패(OOM)**. 상세는 §3.
3. → **이 실측을 근거로 LLM을 GMS API(gpt-5-nano) 호출로 전환하기로 팀 결정(2026-07-24).**
   젯슨에서 LLM RAM이 사라져 **오디오 예상 피크 ~3.3GB(여유 ~4.1GB)**. 오프라인은 명세 33-8
   키워드 폴백(LLM RAM 0)으로 대응. ⚠️ 예상치이므로 GMS 구성으로 §2 재측정 필요.

## 3. ⚠️ 발견: qwen2.5:3b는 page cache 압박 시 GPU 로드 실패

**증상.** 동일 구성에서 LLM 로드가 다음 에러로 실패:

```
cudaMalloc failed: out of memory
failed to allocate CUDA0 buffer of size 1923955712 (1.79GB)
```

**원인.** 당시 메모리 상태는 `free 1.3GB / buff-cache 4.2GB / available 5.0GB`.
"available"은 5GB지만, **젯슨의 CUDA(nvgpu) 할당기는 page cache를 자동 회수하지 못한다.**
그래서 진짜 free(1.3GB)가 요구량(1.79GB)보다 작으면 — 캐시가 아무리 많아도 — 할당이 실패한다.
일반 CPU malloc과 다른 젯슨 특유의 거동이다.

**확인.** `sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'`로 캐시를 비워 free를 5.1GB로
올리자 정상 로드됨. GUI 종료(헤드리스 전환)만으로는 해소되지 않았다.

**함의.** 장시간 운용으로 캐시가 차오르면 현장에서 LLM 로드가 실패할 수 있다 = **배포 리스크.**

**대응 (택1 이상):**
1. LLM 로드 직전 `drop_caches` 실행 (런처 스크립트에 포함)
2. `keep_alive`로 LLM 상주 유지 → 재로드 자체를 회피 (단, 상주 RAM 부담)
3. 1.5b급 다운시프트 → 요구 버퍼가 ~1GB로 줄어 실패 확률 자체가 감소

## 부록 A. 사전 예상치 (실측 전 산정 근거 — 참고용)

실측 전 모델 파라미터 수·양자화 기준으로 산정했던 구성요소별 예상치. §2-2에서 실측과 대조 완료.

| 구성요소 | 예상 RAM | 로드 시점 |
|---|---|---|
| torch + CUDA 컨텍스트 | ~0.4–0.7GB | 시작 시 1회 |
| Python·numpy·librosa 등 | ~0.3–0.5GB | 시작 시 |
| Silero VAD | ~0.1GB | 상주 |
| faster-whisper small (int8) | ~0.8–1.0GB | 상주 |
| MeloTTS (KR) | ~1.3–2.0GB | (미탑재 — 탑재 시 상주) |
| ollama qwen2.5:3b (Q4) | ~2.0–2.4GB | 보고 중에만 |
| ollama qwen2.5:1.5b (Q4) | ~1.0GB | 다운시프트 후보 |

- 개발 PC(x86/float16)와 젯슨(ARM64/int8, 통합메모리)은 메모리 회계가 다르므로 PC 측정값으로 대체 불가.
- `pipeline.py`는 VAD·STT(·TTS 탑재 시 TTS까지)를 import 시점에 상주 로드한다. "순차 실행으로 피크를 낮춘다"는 LLM(ollama)에만 해당.
