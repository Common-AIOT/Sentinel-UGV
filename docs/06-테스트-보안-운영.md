# 16. 테스트 및 검증 계획 [확정]

> 이 장은 요약이다. 시험 ID 정의, 정량 합격 기준, 시험 환경(E1~E4), 단계별 인수 Gate(G0~G7), 최종 시나리오(SCN-01~03)와 3회 연속 성공 규칙의 규범(상세)은 38장(요구사항 추적표·최종 인수 시험)이다. 영상 시험의 정량 기준은 32장에도 정의된다.

핵심 결정:

- 단위 → 컴포넌트 → 벤치 → 시뮬레이션/리플레이 → 통합 → 장애 주입 → 성능 → 시연 리허설 순으로 검증 단계를 올린다(16.1).
- 안전 시험은 구동 바퀴를 띄운 벤치(38-6 환경 E1)에서 시작하고, 낮은 속도의 바닥 시험, 실제 시나리오 순으로 올린다. 앞 Gate의 안전 결함이 남은 상태에서 속도·복잡도를 올리지 않는다.
- 개별 시험의 ID·정량 합격 기준·증빙은 38-3(기능)·38-4(비기능)·38-5(안전) 추적표를 단일 기준으로 삼는다. 이 장의 시험 ID 표는 38장으로 통합되었다.
- 요구사항 상태 전이(PLANNED→IMPLEMENTED→VERIFIED→ACCEPTED)와 재시험 규칙은 38-1 판정 원칙을 따른다.
- 최종 인수는 같은 release·firmware·config로 SCN-01 중심 통합 시연을 3회 연속 성공해야 한다(38-9).

## 16.2 하드웨어 테스트 체크리스트
차량을 바닥에서 띄운 상태에서 시작한다(38-6 환경 E1). ESP32 부팅 시 PWM 0·enable LOW, USB 분리 후 300ms 이내 정지, 12V 배터리 연결 분리 시 모터 정지, 프로그램 종료 시 정지는 38장 CTRL 시험군과 G0~G1 Gate에서 검증한다(**물리 E-Stop 스위치는 미도입이라 그 항목은 없다** — 03장 34-10). 모터 ESP32의 Wi-Fi는 모바일 수동 조종에만 사용하고 자율·정지·watchdog 경로에는 넣지 않는다. Bluetooth는 사용하지 않는다. DHT11·초음파 timeout이 100Hz 센서 태스크를 막지 않는지도 확인한다. 시험 ID가 없는 물리 점검 항목은 다음과 같다.

- □ 후륜 좌·우 구동 모터 방향과 전진·후진 정상 동작 확인
- □ 조향 서보 중립·좌우 엔드포인트 스윕 확인(앞바퀴 띄움, 링키지가 기계 한계를 밀지 않음 — CTRL-24)
- □ 조향 링키지(서보 혼–타이로드) 체결·유격 확인, 왕복 히스테리시스가 `δ_max`의 5% 이내
- □ 앞바퀴 최대 조향 시 초음파 음장·차체 간섭 없음
- □ 후방 초음파(HC-SR04, TBD-HW-010·S15P11A301-324) 음장이 범퍼·후륜에 가리지 않음, 전방 센서와 순차 trigger로 상호 간섭 없음
- □ 급조향 시 배터리 전압 강하로 Jetson·ESP32가 재부팅하지 않음
- □ 배선 발열·커넥터 이탈 없음(BTS7960 ×2, 조향 서보 포함)
- □ Jetson 저전압/재부팅 없음
- □ LiDAR·카메라 고정 마운트 체결 상태와 케이블 여유 확인
- □ LiDAR 스캔을 차체가 가리지 않음

## 16.3 자율주행 테스트
수동 지도 생성, 정적 목표 주행, 장애물 우회, **최소 회전반경 `R_min` 선회와 전·후진 3점 선회**, Frontier 자동 선택·소진, home 복귀, 로컬 센서 장애 시 정지·오류 알림을 검증한다. **제자리 회전은 시험 항목이 아니다**(전륜 조향, 02장 6.3). 시험 ID와 합격 기준은 38-3 추적표의 NAV 시험군과 38-5의 SR-004를 규범으로 한다.

## 16.4 AI·영상 테스트
사람 탐지(정면·측면·부분 가림), 동일 인물 중복 억제, 사람 위치 추정, 다중 인원 encounter, 로컬 WebRTC·원격 EC2 경유 지연, encounter 전후 3초 버퍼, 카메라 단일 오픈(AI와 스트림 동시 안정성), 음성 상호작용(질문·응답·무응답 fallback)을 검증한다. 시험 ID와 측정 기준은 38-3의 AI·VID·VOI 시험군과 32장 VID-01~05 정량 기준을 규범으로 한다.

## 16.5 서버·데이터 테스트
임무 생성부터 종료까지의 상태 일관 저장, MQTT·WSS 재연결 후 최신 상태·pending 이벤트 복구, S3 업로드 실패 시 중복 없는 재시도, Presigned URL 만료·권한, 동일 제어권의 동시 획득 차단은 38-3~38-4의 MIS·NET·MED·SEC·DATA 시험군을 규범으로 한다. 추적표에 없는 점검 항목은 다음과 같다.

# 36. 보안·개인정보·데이터 보호 정책

## 36-1. 범위와 기본 원칙

Sentinel은 사람의 얼굴·음성·위치·부상 관련 응답을 저장할 수 있으므로 일반 센서 로그보다 높은 보호 수준을 적용한다. 다만 본 시스템은 교육·시연용 프로토타입이며 실제 재난 구조 시스템의 법적·의료적 인증을 받은 제품이 아니다.

기본 원칙:

1. 필요한 이벤트 데이터만 수집한다.
2. 실시간 제어와 장기 저장 권한을 분리한다.
3. 인터넷 구간은 TLS로 보호한다.
4. S3 객체는 공개하지 않는다.
5. Jetson에 장기 AWS Access Key를 저장하지 않는다.
6. **인증은 MVP 범위 밖이다 (v2.0 결정).** 운영자 로그인·접근 토큰을 구현하지 않는다. 접근 경계는 EC2 Security Group 의 허용 IP 와 CORS 이며, 조종 충돌은 Control Session 이 중재한다(인증이 아니다). 근거와 남는 위험은 36-4.
7. 시연 종료 후 보존 기간에 따라 영상·음성을 삭제한다.
8. 비밀번호·토큰·Presigned URL·원문 음성을 일반 로그에 남기지 않는다.

## 36-4. MVP 접근 보호와 제어권

> **v2.0 정정 (2026-08-04): 인증이 구현되지 않았다.** 이 절의 v1.1 내용은 계획이었고
> 실행되지 않았다. 명세가 "보호한다"고 적고 있는데 실제로는 열려 있는 것이 이 문서에서
> 가장 위험한 종류의 불일치이므로 **현재 상태를 그대로 적는다.**

### 실제 상태

`backend/src/main/java/com/sentinel/backend/common/config/SecurityConfig.java`:

```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/**", "/actuator/**", "/ws/**",
                         "/swagger-ui/**", "/swagger-ui.html", "/v3/api-docs/**")
        .permitAll()
        .anyRequest().authenticated());
```

| 항목 | v1.1 계획 | 실제 |
|---|---|---|
| 운영자 로그인 (UI + `users` 테이블) | 구현한다 | **없다.** `users` 테이블 자체가 없다 — `V1__init_schema.sql` 둘째 줄이 `users`를 MVP 범위 밖으로 명시적으로 제외한다. 로그인 화면도 없다 |
| 허용 IP 제한 | EC2 Security Group | **없다.** 8080 이 `0.0.0.0/0` 이다 (2026-08-04 확인) |
| 배포 환경 접근 토큰 | Nginx/Spring 검증 | **없다** |
| WebSocket Origin·토큰 검증 | 검증한다 | Origin은 CORS로만 제한. 토큰 검증 **없다** |
| 임무 명령 API | 토큰·세션 없이 공개하지 않는다 | **`/api/**` 전체가 `permitAll()`이다** |
| Control Session | 단일 조종자 세션 | 구현됨. 다만 이것은 **애플리케이션 수준 중재**이고 인증이 아니다 |
| 15분 비활성 만료 | 구현 | **실제는 발급 시점 기준 10분 고정 TTL.** 활동에 따른 연장·heartbeat 회수 없음 |

즉 **접근 통제가 없다.** CORS 는 브라우저에만 적용되므로 `curl` 한 줄에는 아무 효력이 없고, Control Session 은 동시 조종을 중재하는 애플리케이션 규칙이지 인증이 아니다.

> **인터넷의 누구나 임무를 만들고 로봇에 명령을 보낼 수 있다.** EC2 8080 이
> `0.0.0.0/0` 이고 인증이 없다. 남은 것은 주소를 모른다는 사실뿐이며, 그것은
> 보호가 아니다. 실제 차량이 물리적으로 움직이므로 노출 결과가 데이터에 그치지
> 않는다.

### 젯슨 쪽 노출

같은 성격의 노출이 하나 더 있다. `foxglove_bridge`의 8765 포트는 **읽기 인증이 없고**, 젯슨이 공인 IP에 있어 인터넷에서 닿는다. S15P11A301-224에서 TLS를 켜고 쓰기를 막고(`capabilities: [connectionGraph]`) 토픽을 제한했으나 읽기는 열려 있다. S15P11A301-305에서 관제용 `/pose/fused`가 추가돼 현재 화이트리스트는 `/map`·`/pose`·`/pose/fused`·`/scan`·`/tf`·`/tf_static`·`/robot_description` **7개**다. 지도·LiDAR 스캔·TF가 그 대상이다.

**명시적으로 수락한 위험**이다. 실제로 범위를 좁히고 있는 것은 위의 셋(쓰기 차단·토픽 7개·TLS)이며 **없는 것은 인증 하나**다.

**2026-08-06 정정 (S15P11A301-295): "볼 때만 켜고 보고 나면 끈다"는 완화가 아니다.** 이 자리에 그렇게 적혀 있었으나 적용할 수 없다 — 관제 웹의 실시간 지도가 이 브릿지에 직접 붙으므로(04장 8.6, `LiveMap.tsx`) 끄면 지도가 죽는다. `--local` + SSH 터널도 같은 이유로 시연 중에는 쓸 수 없다. 실측: `enable_viz` 기본값이 `true`라 **스택이 뜨면 8765가 `0.0.0.0`에 열린다**(서비스를 `enable` 해 둔 동안에는 부팅만으로도 열린다 — 2026-08-11 확인 시점 `enable` 상태는 `disabled`). 즉 노출 구간은 스택이 떠 있는 동안 전부다. 자세한 내용은 04장 8.5.

### v2.0 결정: 인증을 구현하지 않는다

**MVP 범위에서 제외한다.** 교육·시연용 프로토타입이고 시연이 LAN에서 이루어지므로, 남은 기간에 인증을 새로 만드는 것보다 노출 범위를 좁히는 쪽이 값이 크다. 애매하게 "구현한다"고 적어 두는 것보다 **안 한다고 적는 것이 낫다** — 그래야 위험을 알고 운영한다.

이 결정으로 남는 위험과 그 완화는 다음과 같다.

| 남는 위험 | 완화 |
|---|---|
| 인터넷의 누구나 임무 생성·명령 가능 | **완화 없음 (2026-08-04 현재).** 8080 이 `0.0.0.0/0` 이고 인증도 없다. 아래 "즉시 조치" 참조 |
| 동시 조종 충돌 | Control Session 단일 조종자 중재 + TTL(애플리케이션 수준) |
| 젯슨 8765 무인증 읽기 | **읽기 자체는 완화 없음** — 관제 지도가 이 브릿지에 직접 붙어 상시 개방이다(2026-08-06 정정). 범위만 좁혔다: 쓰기 차단·토픽 7개(`/pose/fused` 포함)·TLS. 카메라 영상은 제외 |
| 평문으로 오간 자격증명 | 시연 후 전부 교체 |

### 즉시 조치

인증을 구현하지 않기로 한 결정은 **EC2 Security Group 이 경계라는 전제**에서 나왔다. 확인 결과 그 전제가 성립하지 않는다. 두 가지 중 하나는 반드시 해야 한다.

- [ ] **8080 인바운드를 좁힌다.** 시연 장소 IP 또는 Vercel 출구 IP + 젯슨 IP. 가장 값싸고 확실하다
- [ ] 좁힐 수 없다면(Vercel 출구 IP 가 고정이 아니다) **명령 계열 엔드포인트에만 공유 토큰을 둔다.** `POST /missions`, `POST /missions/{id}/commands`, `POST /control-sessions` 세 곳이다. 조회는 열어 두어도 피해가 데이터에 그친다

두 번째가 현실적일 가능성이 높다 — Vercel 서버리스 출구 IP 는 고정되지 않으므로 IP 제한만으로는 관제 웹이 막힌다. 헤더 하나 검사하는 필터로 충분하며, 로그인·세션·`users` 테이블은 여전히 필요 없다.

운영 시 확인 항목:

- [ ] 시연 외 시간에는 `sentinel-demo` 전체 스택을 내린다(`foxglove_bridge`는 관제 지도 때문에 시연 중 상시 필요)
- [ ] 시연 후 자격증명 교체 (Docker Hub PAT·MinIO·Vercel·MQTT·DB)

추후 다중 사용자 서비스로 확장할 때 로그인·회원가입·역할 권한 세분화를 별도 설계한다. 그때 `users`·`control_sessions.user_id`·`control_commands.issued_by_user_id` 정의를 그대로 쓸 수 있다(13장에 남겨 두었다).

## 36-5. MQTT 보안

```text
Jetson cloud_bridge
→ MQTT 5 over WSS :443
→ Mosquitto
← Spring Boot service account
```

필수 정책:

- 평문 MQTT 1883 인터넷 공개 금지
- 익명 접속 금지
- Jetson 차량별 계정과 긴 무작위 비밀번호 또는 클라이언트 인증서
- Mosquitto ACL로 차량별 토픽 제한
- Spring Boot 계정과 차량 계정 분리
- `cmd/*` Retain 금지
- TLS 인증서 만료일 모니터링
- ACL 거부 로그 수집(접근 토큰 검증은 미구현)

예시 ACL 의미:

```text
robot SENTINEL-01
  publish: sentinel/v1/robots/SENTINEL-01/presence|state|telemetry|events|acks
  subscribe: sentinel/v1/robots/SENTINEL-01/cmd/*

backend service
  subscribe: sentinel/v1/robots/+/presence|state|telemetry|events|acks
  publish: sentinel/v1/robots/+/cmd/*
```

차량 자격 증명이 노출되면 해당 계정만 비활성화·교체할 수 있어야 한다. 여러 장치가 하나의 MQTT 계정을 공유하지 않는다.

## 36-6. REST·WebSocket·WebRTC 보안

### REST/WSS

> **현재 배포:** `compose.prod.yaml`은 Spring Boot `8080:8080`을 호스트에 직접 공개하며 compose 내 Nginx는 없다. 아래의 토큰·rate limit도 미구현이다.

- PostgreSQL·TimescaleDB는 Docker 내부에 두지만 Spring Boot 8080은 외부에 직접 열려 있다.
- 입력 JSON은 schema, 길이, 범위, enum을 검증한다.
- 명령 요청은 Control Session·`commandId`·TTL 계약을 사용하지만 **접근 토큰은 검증하지 않는다.**
- 오류 응답에 stack trace, DB 쿼리, 내부 IP를 노출하지 않는다.
- 요청 rate limit은 **미구현**이다.

### WebRTC

- Jetson의 WHEP signaling도 HTTPS를 사용한다.
- 관제 노트북에만 신뢰된 로컬 인증서를 설치한다.
- 현재 MediaMTX path 인증·짧은 토큰은 **미구현**이며, 주소를 알면 시청할 수 있다. WHEP TLS만 적용된 수락 위험이다.
- ICE candidate에 불필요한 외부 인터페이스를 노출하지 않는다.
- 원격 TURN을 도입하면 장기 credential을 프론트 코드에 하드코딩하지 않는다.

라이브 영상 연결 실패 때문에 TLS 검증을 끄거나 브라우저 보안 플래그를 비활성화한 상태를 최종 시연 구성으로 사용하지 않는다.

## 36-7. S3·DB 보호

### S3

- Block Public Access 활성화
- 객체 공개 ACL 금지
- HTTPS 전송만 허용
- 기본 서버 측 암호화 사용
- Jetson에는 AWS Access Key를 저장하지 않고 Spring Boot가 짧은 Presigned PUT URL 발급
- 조회도 짧은 Presigned GET URL 사용
- object key는 클라이언트 입력을 그대로 쓰지 않고 서버가 `missionId/encounterId/mediaId`로 생성
- 업로드 완료 시 크기, MIME, SHA-256, `encounterId`를 검증
- Presigned URL 전체를 애플리케이션 로그에 출력하지 않음

권장 만료:

| 용도 | 초기 만료 |
|---|---:|
| 이벤트 업로드 PUT | 10분 |
| 관제 재생 GET | 10분 |
| 썸네일 GET | 10분 |

네트워크 장애로 Presigned URL이 만료되면 기존 URL을 재사용하지 않고 새 URL을 발급한다.

### PostgreSQL·TimescaleDB

- DB는 Docker 내부 또는 사설 네트워크에서만 접근
- 애플리케이션 계정에 필요한 스키마 권한만 부여
- 운영 계정과 migration 계정 분리 권장
- 자동 백업 파일도 같은 수준으로 보호
- transcript 검색을 위해 불필요한 전체 텍스트 인덱스를 만들지 않음
- 직접 DB 조회가 필요하면 팀원별 계정 또는 제한된 읽기 계정 사용

## 36-8. Jetson 로컬 데이터·비밀값

로컬 경로 권장:

```text
/etc/sentinel/secrets/       root:sentinel 0640
/var/lib/sentinel/media/     sentinel:sentinel 0750
/var/lib/sentinel/outbox/    sentinel:sentinel 0750
/var/log/sentinel/           sentinel:adm 0750
```

필수 규칙:

- `.env`, 인증서 private key, MQTT 비밀번호를 Git에 올리지 않는다.
- systemd의 `EnvironmentFile` 또는 읽기 제한된 Secret 파일을 사용한다.
- Jetson shell history에 토큰과 Presigned URL을 직접 입력하지 않는다.
- 업로드 완료된 로컬 영상은 보존 정책에 따라 삭제한다.
- 서비스는 root가 아니라 필요한 장치 그룹만 가진 전용 사용자로 실행한다.
- `/dev/video*`, `/dev/tty*`, GPIO 접근 권한은 그룹과 udev 규칙으로 제한한다.

교육용 장비에서 전체 디스크 암호화를 적용하기 어렵다면 물리 접근 통제와 짧은 로컬 보존을 최소 대책으로 사용한다.

## 36-9. 보존·삭제 정책

다음은 MVP 기본값이며 지도교수·교육기관 정책이 있으면 그 정책을 우선한다.

| 데이터 | 기본 보존 | 삭제 방식 |
|---|---:|---|
| 이벤트 원본 MP4·오디오 | 30일 | S3 Lifecycle + DB 상태 갱신 |
| 썸네일 | 30일 | 원본 이벤트와 함께 삭제 |
| STT transcript | 30일 | interaction turn에서 삭제·비식별화 |
| 피해자 구조화 보고 | 30일 | encounter·victim 연결과 함께 삭제 |
| 임무 지도·경로 | 90일 | 임무 삭제 요청 시 함께 삭제 |
| 일반 telemetry | 30일(정책값) | **자동 retention policy 미설정 — 현재 수동 정리** |
| 운영·보안 로그 | 14일 | rotation·retention |
| 발표용 익명 통계 | 프로젝트 종료까지 | 개인 식별 가능 정보 제거 |

임무 삭제 순서:

```text
DELETE_REQUESTED
→ 제어·업로드 작업 중지 확인
→ S3 객체 삭제
→ media_assets DELETED 확인
→ victim·interaction·encounter 삭제 또는 비식별화
→ telemetry·path 삭제
→ mission 삭제
→ 감사 로그에 결과만 기록
```

삭제가 일부 실패하면 `PARTIAL_DELETE` 상태로 두고 재시도한다. DB 행만 먼저 지워서 S3 고아 객체가 남는 상황을 만들지 않는다.

## 36장 최종 확정안

> Sentinel의 얼굴·음성·위치·부상 응답은 민감 데이터다. 그러나 MVP는 운영자 로그인·접근 토큰·rate limit을 구현하지 않았고 Spring Boot 8080도 호스트에 공개한다. Control Session은 동시 조종을 중재할 뿐 인증이 아니다. MQTT는 WSS 443·차량별 계정·ACL을 사용하고, 미디어는 짧은 Presigned URL로 전송하지만 MediaMTX path 인증은 없다. 30일 보존은 정책값이며 DB retention 자동화는 미구현이다. 이 제한을 수락하고 배포망·시연 운영으로 노출 시간을 줄인다.

# 37. 운영·모니터링·장애 복구 설계

## 37-1. 운영 목표

운영 설계의 목표는 장애를 전부 막는 것이 아니라, **어디가 고장 났는지 빠르게 확인하고 차량을 안전 상태로 만든 뒤 재현 가능한 순서로 복구하는 것**이다.

운영 원칙:

- 부팅·재연결 후 자동 주행 재개 금지
- 모터 enable보다 상태 점검을 먼저 수행
- 프로세스 자동 재시작과 임무 자동 재개를 구분
- 영상·이벤트·제어 상태를 각각 health로 관리
- wall clock은 기록 정렬, monotonic clock은 TTL·watchdog에 사용
- 실패를 숨기지 않고 `DEGRADED`, `FAULT`, `PAUSED`로 명시

---

## 37-2. Jetson 부팅 순서

```mermaid
flowchart TD
    boot["Jetson 부팅"] --> time["systemd-timesyncd·시각 확인"]
    time --> devices["카메라·LiDAR·ESP32 확인"]
    devices --> stm["ESP32 handshake·SAFE_IDLE"]
    stm --> ros["ROS2 센서·TF·오도메트리"]
    ros --> perception["YOLO·영상·MediaMTX"]
    perception --> mission["Mission Manager SAFE_IDLE"]
    mission --> cloud["MQTT·Outbox·S3 uploader"]
    cloud --> ready["READY - 운영자 시작 대기"]
```

세부 순서:

1. OS, NVMe, 네트워크가 올라온다.
2. `systemd-timesyncd`가 동작하고 시각 이상 여부를 기록한다.
3. ESP32는 독립적으로 `SAFE_IDLE`, PWM 0을 유지한다.
4. udev 별칭으로 카메라·LiDAR·ESP32 장치를 확인한다. IMU는 독립 USB 장치가 아니라 센서 ESP32 뒤에 있으므로 별도 udev 장치를 찾지 않는다.
5. ESP32 handshake와 펌웨어 버전을 확인하고 센서 ESP32의 IMU bus·주기·보정 상태를 확인한다.
6. ROS2 센서 driver, robot_state_publisher, TF, `/imu/data_raw`, odometry를 시작한다.
7. SLAM/Nav2 lifecycle node를 inactive 상태로 준비한다.
8. GStreamer, MediaMTX, YOLO, 녹화 링 버퍼를 시작한다.
9. Mission Manager와 안전 노드를 시작한다.
10. MQTT, Outbox worker, S3 uploader를 시작한다.
11. 모든 필수 health가 정상이면 `READY`를 표시한다.
12. 운영자 명령 전까지 모터 enable을 허용하지 않는다.

온습도, S3, EC2 연결 같은 보조 기능이 실패해도 `DEGRADED_READY`로 시작할 수 있지만 ESP32, 엔코더, LiDAR, TF가 실패하면 자율 임무 시작을 차단한다. **E-Stop 은 이 조건에서 뺐다** — 물리 E-Stop 이 미도입이라 판정할 대상이 없다(03장 34-10).

## 37-3. systemd 서비스 구조

> **v2.0 정정 (2026-08-04):** 유닛이 **1개 구현돼 있다.**
> `scripts/systemd/sentinel-demo.service`가 S15P11A301-156에서 만들어졌다.
> v1.1의 "구현된 유닛은 없다"는 무효다.
>
> 아래 9개로 쪼개는 구조는 채택하지 않았다. 실제 구조는 **단일 진입점**이다.
>
> ```text
> sentinel-demo.service  →  scripts/demo_up.sh  →  ros2 launch sentinel_bringup demo.launch.py
> ```
>
> 노드별 유닛으로 쪼개지 않은 이유는 launch 파일이 이미 의존 순서와 시작 지연을
> 관리하고 있고, 유닛 9개로 나누면 그 순서를 두 곳에서 관리하게 되기 때문이다.
> 유닛은 **기본 비활성**이며(`systemctl enable`을 하지 않는다) 손으로 올릴 때는
> `./scripts/demo_up.sh`, 내릴 때는 `./scripts/demo_down.sh`를 쓴다.
>
> `demo_down.sh`는 내린 뒤 **다시 훑어서 남은 프로세스가 있으면 0이 아닌 값으로 종료한다.**
> 예전에는 "내렸다"만 출력하고 1601MB짜리 탐지 프로세스가 살아남는 일이 있었다.
>
> MVP가 자동 복구를 구현하지 않으므로 `Restart` 정책의 이점은 여전히 작다. 개발 중에는
> 오히려 방해가 된다(로그가 `journalctl`로 가고, `Restart`가 죽인 프로세스를 되살려
> 디버깅이 꼬인다). 38장 인수 시험에 systemd를 요구하는 항목도 없다.
>
> **안전은 영향받지 않는다.** 아래 정책의 두 번째 항목대로 `esp32-motor-bridge`가 죽어도
> 모터 ESP32 watchdog이 모터를 정지시킨다. systemd는 그 근거가 아니다.

### 37-3-1. 부팅 자동 기동은 시각 동기 뒤여야 한다 (2026-08-06, S15P11A301-306)

**이 젯슨은 RTC 백업 배터리가 없어 부팅할 때마다 시계가 두 번 점프한다.** 유닛을
`enable`해 둔 채 부팅하면 스택이 그 두 점프 **사이**에 뜨고, 두 번째 점프가 이미
돌고 있는 ROS 그래프를 부순다. 2026-08-06 실측(부팅 자동 기동, 저널 기준):

```text
1970-01-01 09:00:41  커널 부팅, 시계 = epoch
1970-01-01 09:00:41  timesyncd: "System clock time unset or jumped backwards,
                     restoring from recorded timestamp: 2026-08-06 13:57:18"
──── 1차 점프(56년). NTP가 아니라 마지막 기록 시각 복원일 뿐이다 ────
2026-08-06 13:57:18  Reached target System Time Set
2026-08-06 13:57:24  Started Sentinel UGV demo stack
2026-08-06 13:57:38  ROS 노드 기동
2026-08-06 14:01:12  timesyncd: Initial synchronization to 192.168.0.1
──── 2차 점프(+3분 22초). 스택이 이미 4분째 돌던 중이다 ────
```

직전 부팅도 같았다(13:44:59 기동 → 13:49:17에 +3분 52초). **재현된다.**

ROS 2는 시스템 시계로 스탬프를 찍으므로 2차 점프가 그대로 파손이 된다. 증상이
전부 다른 곳에서 나타나 시계를 의심하기 어렵다는 것이 이 항목의 요점이다:

| 관측된 로그 | 실제 원인 |
| --- | --- |
| `slam_toolbox: the timestamp on the message is earlier than all the data in the transform cache` | TF 캐시가 미래 시각으로 채워져 라이다 스캔을 전량 폐기 → **지도가 안 나온다** |
| `stream_pipeline: 입력이 232.0초간 없다. 1.0초 후 재시작` | `now - 마지막프레임시각`이 점프량만큼 커져 입력 타임아웃 오판 → 파이프라인 재시작 |

**`esp32_sensor_bridge: 핸드셰이크 완료` 반복은 이 표에서 뺐다(2026-08-06 정정).**
처음에는 워치독 오판에 의한 재핸드셰이크 폭주로 읽고 증상에 넣었는데, **시각 동기가
끝난 뒤 뜬 스택에서도 같은 빈도로 계속 찍힌다** — 아래 검증에서 최근 60초에 400건
(6.7Hz)이었고 그때 시계는 `synchronized: yes`였다. 원인은 시계가 아니라
`esp32_bridge.yaml`의 `keepalive_period_s: 0.15`다. 150ms마다 HELLO를 보내고
`_handle_hello_ack`가 ACK마다 INFO를 찍으므로 1/0.15 = 6.7Hz가 **정상 동작**이다.
그 상태에서 센서 값도 정상이었다(온도 24.0℃, 습도 64.0%, `mcuConnected: true`).

즉 로그가 시끄러운 것이지 연결이 끊기는 것이 아니다. 이 문장을 남기는 이유는 같은
로그를 보고 시계를 다시 의심하는 일을 막기 위해서다. 로그 수준을 낮추는 것은 별건이다.

**손으로 `demo_down.sh` 뒤 `demo_up.sh` 하면 멀쩡한 이유가 이것이다** — 그 시점에는
NTP가 이미 맞아 있어 남은 점프가 없다. 스크립트 차이가 아니라 **기동 시점 차이**이며,
"부팅으로 뜬 스택만 이상하다"는 관측은 정확했다.

조치는 유닛을 `time-sync.target` 뒤로 보내는 것이다. 다만 **`time-sync.target`만으로는
아무 보장이 없다** — `systemd-time-wait-sync.service`가 disabled면(Ubuntu 기본값) 이
target은 즉시 도달하고, 저널의 `Reached target System Time Set`은 "NTP 동기 완료"가
아니라 "시계에 값이 들어갔다"는 뜻일 뿐이다. 그래서 둘이 **함께** 가야 한다:

```bash
sudo systemctl enable systemd-time-wait-sync.service
sudo mkdir -p /etc/systemd/system/systemd-time-wait-sync.service.d
sudo cp scripts/systemd/systemd-time-wait-sync-timeout.conf \
     /etc/systemd/system/systemd-time-wait-sync.service.d/timeout.conf
sudo cp scripts/systemd/sentinel-demo.service /etc/systemd/system/
sudo systemctl daemon-reload
```

**`TimeoutStartSec` 상한이 반드시 따라와야 한다.** 배포판이 주는
`systemd-time-wait-sync.service`는 `TimeoutStartSec=infinity`라 NTP가 없으면 무한정
기다린다. 상한 없이 유닛을 `time-sync.target` 뒤로 보내면, 시연장에 NTP가 없을 때
스택이 **틀린 시계로 뜨는 것이 아니라 아예 뜨지 않는다** — 고치려던 것보다 나쁜
실패다. 90초로 잡은 근거는 `scripts/systemd/systemd-time-wait-sync-timeout.conf`에 있다.

**남는 제약.** RTC 백업 배터리를 달면 1차 점프(56년)가 사라지고 2차 점프도 수 초로
줄어든다. 위 조치는 배터리 없이 증상을 막는 쪽이므로 배터리 장착은 별건으로 남는다.
상한에 걸려 시각 동기 없이 뜬 경우에는 동기가 붙은 뒤 손으로 `demo_down.sh` →
`demo_up.sh` 해야 한다.

**검증(2026-08-06 15:01 재부팅, 부팅 자동 기동).** 스택이 동기 **뒤에** 떴다.

```text
15:01:06  systemd-timesyncd 시작
15:01:38  timesyncd: Initial synchronization to time server 192.168.0.1:123
15:01:38  Finished Wait Until Kernel Time Synchronized
15:01:38  Started Sentinel UGV demo stack
```

`timedatectl`이 `System clock synchronized: yes`다. 동기 대기는 **32초**로 90초 상한에
닿지 않았다 — 이 값은 NTP가 `192.168.0.1`인 이 네트워크의 실측이며, 시연장 네트워크가
다르면 다시 재야 한다.

같은 세션에서 위 표의 두 증상은 나오지 않았다(`transform cache` 0건, `입력이 …초간
없다` 0건). 다만 조치 전 세션에서도 각 1건이었으므로 **표본이 작다** — 이 수치만으로
재발 없음을 단정하지 않는다. 판단 근거는 기동 순서(위 저널)가 먼저다.

아래는 채택하지 않은 v1.1 설계다. 향후 쪼갤 필요가 생길 때의 참고로만 남긴다.

권장 서비스:

```text
sentinel-esp32-motor-bridge.service
sentinel-esp32-sensor-bridge.service
sentinel-ros-bringup.service
sentinel-media.service
sentinel-perception.service
sentinel-mission.service
sentinel-cloud-bridge.service
sentinel-uploader.service
sentinel-health-agent.service
```

의존 관계:

```text
esp32-motor-bridge
esp32-sensor-bridge
├─ ros-bringup
│  ├─ perception
│  └─ mission
├─ media
└─ cloud-bridge
   └─ uploader
```

정책:

- 비안전 서비스는 `Restart=on-failure`와 지수 백오프를 사용한다.
- `esp32-motor-bridge`가 죽어도 모터 ESP32 watchdog이 모터를 정지한다. `esp32-sensor-bridge`가 죽으면 엔코더·IMU·환경·근접 데이터가 끊겨 Jetson이 AUTO를 PAUSED로 전환한다.
- `ExecStop`과 signal handler는 STOP을 보내되 이것만 안전 근거로 삼지 않는다.
- 반복 실패 횟수가 임계값을 넘으면 무한 재시작 대신 `FAILED`로 남기고 관제에 원인을 표시한다.
- 서비스 파일과 환경변수는 Git에서 template로 관리하고 secret은 분리한다.

프로세스 재시작 후 Mission Manager는 `SAFE_IDLE`(임무 이력 없음) 또는 `PAUSED`(복구된 임무 존재)로 복구한다. 복구 진입 여부는 상태 필드가 아니라 이벤트 로그(`RECOVERED_FROM_RESTART`)로 기록한다. 표준 상태 머신(14.1·26.2)에 없는 별도 상태를 도입하지 않으며, 재부팅 전의 AUTO/MANUAL 동작을 자동으로 이어서 실행하지 않는다.

### 37-3-2. 스택 두 벌이 겹치면 증상이 「주행이 안 된다」로 나온다 (2026-08-07, S15P11A301-338)

`demo_up.sh`에는 S15P11A301-294부터 이중 기동 거부가 있었지만 **`systemd` 서비스만
보았다.** 손으로 두 번 부르면 둘 다 서비스가 아니라 둘 다 통과한다. 2026-08-07
주행 시험에서 20초 간격으로 두 번 불러 두 벌이 **7분 10초** 겹쳤다.

겹칠 때 실제로 깨지는 것과 그때 보이는 증상이다. **어느 것도 "두 벌이 떴다"로는
보이지 않는다** — 그래서 원인 조사에 리허설 하나를 버렸고, 다른 파트는 이것을
「`mission_manager`가 임무 시작 직후 죽었다」로 보고했다(로그에 예외는 없었고 노드는
살아 있었다).

| 겹치는 자원 | 무엇이 깨지나 | 보이는 증상 |
| --- | --- | --- |
| `/dev/sentinel_mcu_motor` | `esp32_motor_bridge` 둘이 같은 포트를 읽어 서로 바이트를 훔친다 | `DRIVE_STATE 가 0.5~0.8초 끊겼다` 반복, 주행 명령이 보드에 온전히 안 간다 |
| `/mission/status` | 발행자가 둘이고 하나는 임무 보유, 하나는 `SAFE_IDLE` | 진단하는 쪽이 어느 값을 읽을지 정해지지 않는다(`missionId: null`로 보인다) |
| MQTT client id | 둘이 같은 ID(`{robot_id}-bridge`)로 붙어 서로를 끊는다 | 2.6초 주기 재연결 146회, 명령이 `PENDING`으로 남는다 |
| `/dev/shm` DDS 세그먼트 | 한쪽을 강제 종료하면 세그먼트가 남는다 | 노드는 다 살아 있는데 `ros2 node list`가 0개다 |

막는 곳은 **기동 지점**이다. MQTT client id를 인스턴스별로 유일하게 만드는 쪽은
택하지 않았다 — 지금 동작(같은 ID는 서로 끊는다)이 오히려 중복을 드러내는 신호이고,
유일하게 만들면 두 벌이 조용히 공존해 진단이 더 어려워진다.

`demo_up.sh`는 두 가지를 본다. **둘 다 필요하다.**

- **`flock` 잠금**(`$XDG_RUNTIME_DIR/sentinel-demo.lock`). `exec 9>`로 연 fd는
  `exec ros2 launch` 이후에도 살아 있어 스택 수명 동안 잠기고, 프로세스가 어떻게
  죽든 커널이 놓는다. PID 파일을 쓰지 않은 이유는 강제 종료 뒤 남아서 **다음 기동을
  잘못 막기** 때문이다. 이 잠금은 노드가 아직 안 뜬 기동 중 구간을 덮는다.
- **도는 프로세스 존재**. 이 스크립트를 거치지 않고 `ros2 launch`를 직접 부른 스택은
  잠금을 잡지 않으므로 잠금만으로는 못 본다. **특정 노드 하나를 기준으로 삼을 수 없다** —
  `enable_mission`을 포함해 `enable_*` 인자가 15개이고 어느 노드든 꺼질 수 있다. 그래서
  두 갈래로 본다: **launch 부모**(인자와 무관하게 스택마다 정확히 하나 — 정상 경로를
  덮는다)와 **`install/sentinel_*/lib/` 아래 노드**(launch 부모가 죽고 노드만 남은 상태를
  덮는다. 2026-08-07에 실제로 그 상태를 만났다). 패키지를 특정하지 않고 경로로 잡으므로
  어떤 조합으로 띄워도 최소 하나는 걸리고, **다른 워크스페이스 사본에서 띄운 스택도
  걸린다** — 같은 시리얼 포트와 같은 DDS 도메인을 쓰는 한 그것도 중복이다.
  패턴은 **파이썬 인터프리터에 앵커한다** — `pgrep -f`는 명령줄 전체를 보므로 앵커가
  없으면 그 문자열을 인자로 가진 셸까지 잡는다(검증 중 실제로 자기 자신을 잡았다).

`demo_down.sh`는 **두 벌 이상이어도 전부 내린다.** 정리 대상을 launch 부모의 자식
트리로 찾지 않고 `ps -e` 전체에서 **경로 패턴으로** 모으기 때문에 인스턴스 수와
무관하다 — SIGINT도 배열로 모든 launch 부모에 보내고, 마지막에 다시 훑어 남은 것이
있으면 0이 아닌 값으로 끝낸다. 그래서 두 번째 스택이 조용히 남을 수 없다.
**남는 위험은 인스턴스 수가 아니라 패턴 목록이 손으로 관리된다는 것이다** — 목록에
없는 노드는 몇 벌이 떠 있든 살아남는다(실제로 `usb_cam`과 `-m src.ros_main`을 빠뜨린
사고가 각각 있었다).

우회는 `SENTINEL_ALLOW_MULTIPLE=1`이다(두 벌을 일부러 띄워 이 사고를 재현하는 것은
정당한 사용이며, 건너뛴 사실을 경고로 남긴다).

#### 시리얼 포트는 장치 단위로도 잠근다 (2026-08-08, S15P11A301-340)

위 기동 지점 방어와 **별개의 층**이다. 브리지가 포트를 `exclusive=True`(POSIX
`TIOCEXCL`)로 열어, 두 번째 프로세스가 같은 tty를 여는 것 자체를 커널이 막는다.

**왜 두 층이 다 필요한가.** 338은 스택 단위라 `demo_up.sh`를 거치는 경로만 막는다.
장치 단위 잠금은 `ros2 run`으로 브리지만 손으로 띄우는 경우, 디버깅용
`picocom`·`minicom`, 다른 워크스페이스 사본까지 전부 막는다.

**중복 열기가 왜 그렇게 나빴는가** — 2026-08-07 사고의 인과가 여기 있다:

```
두 브리지가 같은 tty → 각자 바이트를 일부만 받음 → 프레임 깨짐
  → 링크가 죽은 줄 알고 재연결 → 포트를 여는 순간 DTR/RTS가 auto-reset 회로를 때림
  → 보드 하드웨어 리셋 → 반복
```

**재연결 한 번이 보드 리셋 한 번이다.** 재연결 주기(`reconnect_delay` 1.0 +
`_BOOT_SETTLE_S` 1.5 = 2.5초)가 관측된 재부팅 주기와 정확히 일치한 것이 이 진단의
근거다. 센서 보드가 73초 동안 29회 재부팅했고, 재부팅마다 브리지가
`reset_encoder_origin()`을 불러 그 구간 이동량이 버려져 **오도메트리 실측이 통째로
오염됐다**(S15P11A301-337·339에서 잘못된 결론 두 개를 만들었다).

**실패 사유를 가른다.** 종전에는 「보드가 안 꽂혔다」와 「남이 쓰고 있다」가 둘 다
`not available`로 나와 아무 단서도 주지 못했다. 포트가 존재하는데 열리지 않으면
점유가 유일하게 가능한 원인이므로, 그때는 `demo_down.sh --dry-run`을 안내하는
문구를 낸다.

**DTR 리셋 자체는 건드리지 않았다.** 보드 기동이 현재 그 리셋과 1.5초 정착에
의존해 동작하고(ROM 부팅 배너를 프레임으로 오인하지 않으려는 근거가 그 주석에
있다), 바꾸려면 실기동 검증이 필요하다. 배타 점유만으로 이 사고는 막힌다.

**`/dev/shm`은 통째로 지우면 안 된다.** 이 젯슨에는 Tegra IPC 세그먼트가 함께 있다
(`nvsci*`·`nvmap_sciipc*`·`ipc_test*`·`itc_test*` 43개, 부팅 시 Tegra 스택이 만든다).
지우면 카메라·GPU 경로가 깨진다. `demo_down.sh`는 정리 검증(위 3단계)을 통과한 뒤
`fastrtps_*`·`sem.fastrtps_*`만 지우며, **`fuser`로 사용자가 없는 것만** 지운다 —
살아 있는 참가자의 세그먼트를 지우면 그 노드가 깨진다. 용량 문제가 아니다(3.8G 중 20M).

## 37-4. EC2 시작·종료 순서

Docker Compose 시작 순서:

```text
PostgreSQL + TimescaleDB healthy
→ Mosquitto healthy
→ Spring Boot 기동(내장 Flyway migration) 및 healthy
→ MinIO healthy
```

Next.js는 Vercel에서 배포하며 Nginx·EC2 MediaMTX는 현재 compose 서비스가 아니다.

중지 순서:

1. 새로운 임무·제어 세션 생성을 차단한다.
2. 활성 Control Session에 STOP을 보내고 만료시킨다.
3. Spring Boot가 Outbox·DB 작업을 마무리한다.
4. Next.js·Spring Boot·Mosquitto를 중지한다.
5. 마지막에 DB를 중지한다.

배포 중 서버가 잠시 내려가도 Jetson의 현재 자율 임무를 강제로 계속하게 두지 않는다. 최신 안전 정책에 따라 EC2 연결 단절 시 로컬 자율 탐사를 계속할 수 있으나, 수동 조작 중 연결이 끊기면 300ms TTL로 정지하고 `PAUSED`로 전환한다.

## 37-5. Health 모델

health는 단순 Boolean이 아니라 다음 상태를 사용한다.

```text
OK
DEGRADED
FAILED
UNKNOWN
```

| 컴포넌트 | 확인 항목 | FAILED 시 |
|---|---|---|
| ESP32 | heartbeat, firmware, fault (`ESTOP_ACTIVE` 는 소프트웨어 latch 비트다 — 물리 입력은 없다, 03장 34-9·34-10) | 모터 정지, 임무 불가 |
| Encoder | tick 변화·방향·불연속 | AUTO 중지 |
| LiDAR | `/scan` 주기·범위 | AUTO 중지 |
| Camera | frame 주기 | 탐사 일시정지 |
| IMU(센서 ESP32 경유) | `/imu/data_raw` 주기·NaN·bias·sequence·측정 timestamp·stale | 융합 축소 또는 AUTO 중지 |
| SLAM | pose update·scan matching | PAUSED |
| Nav2 | lifecycle·action 상태 | 목표 취소·PAUSED |
| YOLO | inference heartbeat | 탐사는 정책에 따라 일시정지, 사람 탐지 불가 경고 |
| MediaMTX | publisher·viewer·frame age | 수동 영상 경고. 수동 경로는 Jetson을 우회하므로 전진 차단 불가(SR-010) |
| Ring buffer | 최근 조각·쓰기 지연 | 녹화 오류 경고 |
| MQTT | 연결·마지막 ACK | 관제 OFFLINE, 로컬 정책 적용 |
| Outbox | pending 개수·최고 age | 업로드 지연 경고 |
| DB/S3 | 요청 성공률·지연 | 로컬 저장·재시도 |

로봇 종합 상태:

```text
READY       = 모든 필수 health OK
DEGRADED    = 보조 기능 실패, 안전 주행 가능
PAUSED      = 임무 진행 불가, 모터 정지
FAULT       = 수동 확인·reset 없이는 복구 불가
ESTOP       = 물리/소프트웨어 E-Stop latch
```

## 37-7. 로그 정책

공통 로그 필드:

```json
{
  "timestamp": "2026-07-22T08:10:01.123Z",
  "level": "ERROR",
  "component": "esp32_motor_bridge",
  "robotId": "SENTINEL-01",
  "missionId": "...",
  "eventCode": "ESP32_COMM_TIMEOUT",
  "message": "No valid drive state for 320ms",
  "context": {"lastSequence": 1832}
}
```

로그에 넣지 않는 값:

- DB·MQTT 비밀번호
- MQTT credential
- 배포 환경 접근 token
- Presigned URL 전체
- 피해자 음성 원문
- transcript 전체 문장

Jetson은 journald와 파일 rotation을 사용하고, 14일 또는 용량 상한 중 먼저 도달한 기준으로 정리한다. 안전 이벤트와 임무 이벤트는 일반 debug 로그와 별도로 DB에 구조화하여 보존한다.

주요 확인 명령:

```bash
systemctl --failed
journalctl -u sentinel-demo -f
ros2 node list
ros2 topic hz /scan
ros2 topic echo /diagnostics
tegrastats
df -h /var/lib/sentinel
sudo docker compose ps
sudo docker compose logs --since=10m backend
```

### ESP32 링크가 조용할 때 `/diagnostics` 를 먼저 읽는다 (S15P11A301-323)

「보드가 말이 없다」와 「말은 하는데 우리가 버린다」는 토픽만 보면 똑같이 조용하다.
그 구분을 진단 항목이 답한다 — **추측하기 전에 이것부터 본다.**

| 항목 | 값 | 읽는 법 |
|---|---|---|
| `esp32_bridge: MOTOR_LINK` | `rx_frame_count = 0` | 바이트가 오지 않는다. 보드 전원·펌웨어·USB 배선 |
| | `rx_frame_count > 0`·`parse_error_count > 0`·`handshake_ok=False` | 프레임은 오는데 해석이 안 된다. 보레이트·프로토콜 버전·보드 역할 |
| | `handshake_ok=False`·`parse_error_count = 0` | HELLO_ACK 만 없다 |
| `esp32_bridge: ENVIRONMENT` | `received_count = 0` | ENVIRONMENT_STATE 프레임 자체가 안 온다 |
| | `received_count > 0`·`published_count = 0` | 전부 버렸다 — DHT 가 유효값을 못 낸다 |
| | `dropped_count > 0`·`published_count > 0` | 간헐 실패. 비율을 본다 |

**`MOTOR_LINK` 는 보드가 죽어 있어도 나온다.** 종전에는 보드의 DIAGNOSTIC 프레임을
받았을 때만 발행해서 무응답이면 항목이 아예 없었고, 「항목 없음」은 화면에서 「정상」과
구별되지 않았다(2026-08-06 모터 보드 무응답 진단이 그래서 길어졌다).

실측 확인(2026-08-07, 실제 무응답 보드):

```text
[esp32_bridge: MOTOR_LINK] level=ERROR
  보드 무응답 — 프레임을 한 번도 받지 못했다. 전원·펌웨어·USB 배선을 확인하라(수신 바이트가 없다)
    handshake_ok=False  rx_frame_count=0  parse_error_count=0  hello_sent_count=10
```

## 37-9. 시각 동기화

Jetson은 systemd-timesyncd, EC2는 배포 환경의 NTP로 UTC 시각을 맞춘다.

- `occurredAt`: 사건이 실제 발생한 Jetson 시각
- `receivedAt`: 서버 수신 시각
- `senderUptimeMs`: 장치 부팅 후 monotonic 시간
- TTL·watchdog: wall clock이 아니라 monotonic clock

시각 오차가 1초를 넘으면 관제에 경고하고, 5초를 넘으면 이벤트 타임라인을 `TIME_UNSYNCED`로 표시한다. 제어 TTL은 시각 동기화가 틀려도 로컬 monotonic 시간으로 안전하게 만료되어야 한다.

## 37-10. Outbox와 미디어 복구

SQLite Outbox의 **실제 스키마**:

```text
message_id PRIMARY KEY
channel
payload
created_at
attempts
last_error
```

상태·`next_attempt_at`·dead-letter 컬럼은 없다. worker가 **5초 주기로 최대 20건**을 flush하고, 성공한 행은 삭제한다. `message_id`를 유지해 중복 저장을 방지한다.

부팅 시 미디어 복구 순서:

1. `.partial` 파일과 segment manifest 검색
2. 참조 조각 존재 여부 확인
3. 재다중화 가능한 이벤트는 MP4 복구
4. checksum 계산
5. DB/Outbox와 미디어 상태 대조
6. 업로드되지 않은 파일을 `UPLOAD_PENDING`으로 재등록
7. 복구 불가 파일은 `CORRUPT`, 원인과 조각 목록 기록

## 37-11. 배포·롤백

### EC2

- Docker image에 `latest`만 사용하지 않고 commit SHA 또는 release tag를 부여한다.
- DB migration은 배포 전에 백업과 하위 호환성을 확인한다.
- health check 실패 시 이전 Compose image tag로 되돌린다.
- migration이 비가역이면 롤백 스크립트 또는 복원 절차를 함께 준비한다.

### Jetson

- ROS2 package, Python venv, MediaMTX binary, config version을 release 단위로 묶는다.
- 현재 동작 버전과 이전 정상 버전을 각각 유지한다.
- 배포 중 모터는 SAFE_IDLE로 두고 구동 바퀴를 바닥에서 띄운다.
- ESP32 firmware와 Jetson protocol version 호환표를 확인한다.
- firmware update 실패 시 ST-Link 등 유선 복구 경로를 문서화한다.

배포 완료는 프로세스가 실행되었다는 사실이 아니라 `ESP32 handshake → 센서 health → 로컬 영상 → 가짜 임무 명령 → STOP` smoke test 통과로 판정한다.

## 37장 최종 확정안

> Jetson은 ESP32 SAFE_IDLE과 장치 인식부터 시작해 ROS2, 영상·AI, Mission Manager, 클라우드 연결 순서로 부팅하며 운영자 명령 전에는 모터를 enable하지 않는다. 각 컴포넌트는 OK·DEGRADED·FAILED·UNKNOWN 상태와 정량 임계값을 가지며, 장애 후 서비스는 재시작할 수 있어도 주행은 자동 재개하지 않는다. 중요 이벤트와 영상은 SQLite Outbox와 로컬 조각으로 복구하고, 배포 실패 시 이전 release·firmware·config 묶음으로 롤백한다.

# 38. 요구사항 추적표·최종 인수 시험

## 38-1. 목적과 판정 원칙

본 장은 요구사항, 구현 모듈, 시험, 정량 합격 기준, 증빙을 연결한다. 코드가 merge되었거나 한 번 동작했다는 사실만으로 완료 처리하지 않는다.

요구사항 상태:

```text
PLANNED
IMPLEMENTED
VERIFIED
ACCEPTED
DEFERRED
FAILED
```

판정 원칙:

- `IMPLEMENTED`: 실제 하드웨어 또는 지정된 통합 환경에서 기능이 실행됨
- `VERIFIED`: 연결된 시험과 정량 기준을 통과하고 증빙이 있음
- `ACCEPTED`: 전체 시나리오와 회귀 시험까지 통과해 팀이 최종 승인함
- `DEFERRED`: 선택·확장 기능으로 최종 시연 범위에서 제외하고 이유가 기록됨
- 시험 실패 후 코드·배선·파라미터를 바꾸면 영향받는 시험을 다시 수행함
- 3회 연속 시연 중 설정을 바꾸면 연속 성공 횟수를 0으로 초기화함

| SR-008 | E-Stop 해제 후, **그리고 수동 종료 후** 자동 재출발 금지 | CTRL-09, CTRL-32 | E-Stop 해제는 SAFE_IDLE 유지. **수동 종료(관제 「자율」)는 `PAUSED` 에 착지하며 절대 `EXPLORING` 이 아니다** — 주행 재개는 별도 `RESUME` 이다(S15P11A301-298) |
| SR-009 | 사람 접근 안전거리 | CAL-10 | 1.5~2.0m 범위 5/5회 정지. **초음파로는 판정할 수 없다** — 그 거리에서 탐지율이 7~27%다(S15P11A301-272, 04장 22.2). LiDAR·사람 탐지 기반 접근 제어의 몫이다 |
| SR-010 | 영상 상실 시 수동 전진 차단 | VID-10 | ~~frame age 3초 후 신규 전진 명령 거부~~ **구조적으로 불가능** — 위 대조표 참고. 젯슨은 수동 경로에 없다 |

### 수동 조종 보호 공백 (S15P11A301-298)

수동 상한을 0.30m/s 로 **유지하기로 한 결정의 대가**다. 없는 보호를 있다고 말하지
않기 위해 여기에 전부 적는다. 04장 14.4 의 안전 우선순위 표와 반드시 함께 읽는다.

| 수동 조종에서 무엇이 보호하지 않는가 | 근거 |
|---|---|
| 라이다 정지·감속 구역 (`collision_monitor`, 정지 x −0.35~+1.05·감속 −0.55~+1.30 — 실측 차체 기준, 후방 포함) | 명령이 `/cmd_vel_muxed` 를 거치지 않는다(04장 24.1) |
| 속도·가감속 상한 (`velocity_smoother`, `max_drive_mmps=300`) | 같은 이유. 0.30m/s 는 앱과 펌웨어가 지킨다 |
| 소프트 E-Stop / `safety_gate` (TTL·임무 상태·`/scan` 침묵) | 같은 이유. `MOVEMENT[MANUAL]=false` 는 「젯슨이 명령을 안 낸다」는 뜻일 뿐이다 |
| 전방 초음파(HC-SR04) 근거리 보호 | 센서 ESP32 에 달려 있고 모터 보드로 직접 배선이 없다(TBD-HW-011). 빈 공간 오측 때문에 `PROXIMITY_STOP_ENABLED=false`로 발동을 껐으며, 남아 있는 젯슨 중계도 신호가 항상 0이라 동작하지 않는다 |
| 가속 제한 | `DriveCommand.maxAccelMmps2` 는 파싱만 되고 어디서도 쓰이지 않는다. 정지에서 full `lin` 은 PWM 계단 입력이다 |
| 전류·스톨·저전압·드라이버 fault 감지 | `DRIVER_FAULT`·`OVERCURRENT`·`UNDERVOLTAGE` 는 정의만 되고 세워지지 않으며 `FAULT_LATCHED` 는 진입되지 않는다 |
| 후방 센싱 | 전혀 없다(04장 24.1 정지 구역 절). **그런데 수동은 후진하는 모드다** — 정지 구역 탈출이 후진뿐이다 |
| 사람 접근 안전거리(SR-009) / 영상 상실 시 전진 차단(SR-010) | 판정 지점이 자율 경로에만 있다. SR-010 은 구조적으로 불가능 |
| 단일 조종자 강제 (FR-012) | 앱 경로에 control session 이 없다. 영구 미충족 |
| 조향 실패 감지 | `STEERING_RESPONSE_MISMATCH` 미구현. 링키지가 빠져도 전기적으로는 정상으로 보인다 |
| 보안 | 폰 핫스팟에 붙은 누구나 로봇을 몰 수 있다. WPA2 암호가 인증 경계 전부이고 로컬 `sid` 는 단일 조종자만 강제하며 신원이 아니다 |

**남는 보호**: 모터 ESP32 fault·통신 워치독, BTS7960 드라이버 fault,
초음파 중계의 순간 정지. 즉 **수동 조종은 사람이 보면서 하는 조작이라는 전제 위에
있다.** 관제 화면(ModeRow)에도 이 사실을 한 줄로 표시한다.

> **기록만 하고 고치지 않는 불일치.** 젯슨 `message_mapper` 는 `MANUAL` 을
> `safetyState = RUNNING` 으로 옮기고(사람이 굴리고 있을 수 있으므로 「멈춰 있다」로
> 보고하지 않는다), 관제 `RobotContext` 는 같은 상태를 `STOPPED` 로 계산한다
> (`EXPLORING`·`RETURNING` 이 아니면 정지로 본다). 두 값이 어긋나지만 **프런트가 로봇의
> `safetyState` 를 아예 수용하지 않으므로** 화면에 드러나지 않는다. 언젠가 그 필드를
> 쓰기 시작하면 이 항목부터 정리한다.

| SR-011 | 과열·저전압 보호 | THM-01/PWR-01 | 임계값에서 감속·PAUSED·정지 정책 실행 |
| SR-012 | 방향 전환 보호 | CTRL-13 | 전진↔후진 전 중립·감속, 과전류 없음 |
| SR-013 | 조향 계통 고장 감지 | CTRL-27 | 링키지 이탈 시 `STEERING_RESPONSE_MISMATCH` 후 자동 주행 중지. **선회를 시도해야 판정되며 직진 중에는 감지되지 않는다**(03장 34-9). 명세이며 미구현 |
| SR-014 | 정지 시 조향각 유지 | CTRL-26 | 통신 단절·정지 명령에서 조향이 중립으로 튀지 않음(관성 주행 궤적 예측 가능성, 03장 34-7) |

안전 시험은 구동 바퀴를 띄운 벤치 시험에서 시작하고, 낮은 속도의 바닥 시험, 실제 시나리오 순으로 올린다.

## 38-12. 알려진 제한사항

최종 명세서에는 다음을 숨기지 않고 기록한다.

- 실제 붕괴 현장용 안전·방수·방진·의료 인증 장비가 아니다.
- 실내 복도와 경미한 변형 바닥을 대상으로 하며 계단·큰 잔해·자갈·침수 환경은 제외한다.
- 2D LiDAR는 스캔면 위·아래 장애물을 놓칠 수 있다.
- **전륜 서보 조향 차량이므로 제자리 회전을 할 수 없다.** 최소 회전반경보다 좁은 공간에서 방향을 바꾸려면 전·후진을 섞은 3점 선회가 필요하다. `/range/rear` 관측은 있지만 후방 보호는 없고 전방 보호도 현재 발동 비활성이다(04장 23.6).
- 조향은 **개루프**다. 서보에 외부 각도 피드백이 없어 실제 조향각을 측정하지 못하며, **링키지 이탈·서보 고장을 전기적으로 감지할 수 없다** — IMU 기대 yaw rate 대조로 간접 판정하고 그것도 선회를 시도할 때만 드러난다(03장 34-9).
- 조향 중립 오차·링키지 유격이 직진성과 좌·우 선회 대칭에 직접 영향을 준다. 좌·우 구동 게인으로 이를 덮으면 선회 특성이 비대칭으로 남는다(03장 35-3).
- 후륜에 기계식 차동장치가 없어 선회 시 내·외측 후륜이 노면을 스크럽한다. 이 때문에 엔코더 좌·우 속도 차로 yaw 를 구할 수 없고 **yaw 소스가 IMU 자이로 하나뿐**이다(04장 23.2).
- 전원을 끊으면(배터리 분리) 조향각은 정의되지 않는다 — 서보 전원이 함께 끊겨 앞바퀴가 자유로워진다(03장 34-7). 차단점을 하나로 유지하기로 한 결정의 대가이며, 물리 E-Stop 을 도입하면 같은 대가가 그대로 적용된다.
- 짐벌은 사용하지 않으므로(6.4) 카메라·LiDAR 고정 마운트의 진동·설치각이 곧바로 scan·영상 품질에 영향을 준다.
- 단일 마이크(BRIO 100 내장)로 다중 화자를 구분하지 않는다.
- STT 결과는 의료 진단이나 구조 우선순위 결정에 사용하지 않는다.
- 로컬 WebRTC 성능은 AP 혼잡과 브라우저 환경에 영향을 받는다.
- ESP32·모터 드라이버·정지 구조는 교육용 프로토타입이며 안전 인증 제어기가 아니다. **독립 차단 장치(물리 E-Stop)가 없다는 것이 이 프로토타입의 가장 큰 안전 한계다**(03장 34-10, SR-002 미충족).
- 모터·드라이버·배터리·DC-DC의 모델은 확정했으나(부록 I) 감속비·정지 전류 등 정확한 정격은 실측 전까지 TBD다.
- 원격 EC2 영상 릴레이와 TURN은 선택 기능이다.
