# 객체탐지 데이터셋 선정

Sentinel UGV 객체탐지(person) 학습·검증에 사용할 데이터셋의 조사 결과와 선정 근거입니다.
설계 기준 명세는 [07-AI-탐지-음성.md](../../07-AI-탐지-음성.md) 25장이며, 이 문서는 그 구현에 쓸
데이터를 고르는 판단 근거를 남깁니다. (Jira: S15P11A301-94 / ISSUE-02)

> **조사 시점** 아래 AI-Hub 관련 사실은 2026-07-28에 공식 상세 페이지에서 직접 확인한 값입니다.
> 페이지에 명시되지 않은 항목은 `미상`으로 두었고 추정치를 적지 않았습니다. 데이터셋 페이지는
> 갱신될 수 있으므로 신청 직전에 규모·이용조건을 다시 확인합니다.
>
> **2026-08-04 개정** C(71850)를 실제로 받아 확인한 결과 **bbox가 없었고**, 추가 조사에서
> 더 나은 후보 E(71550)를 찾았습니다. 최초 조사가 후보를 충분히 넓게 잡지 못했습니다.
> 변경된 우선순위는 4절, 실측 결과는 3.1절을 참고하세요.

## 1. 무엇을 위한 데이터인가

이번 스프린트의 탐지 대상은 **person 단일 클래스**입니다(04 25.1). 따라서 데이터셋에 요구하는
최소 조건은 다음과 같습니다.

| 요구 | 이유 |
|---|---|
| 사람 bounding box 라벨 | Detect 학습에 필수 |
| 실내·저조도 유사성 | 밀폐공간 탐색이 목표 도메인 |
| 로컬 다운로드 가능 | 안심존 격리 환경에서는 학습 불가 |
| 명확한 이용 조건 | 산출물 공개 범위에 영향 |

**비정형 자세(누운 사람) 포함 여부가 이번 선정의 핵심 변수입니다.** 사유는 3절 참고.

### A — 스마트 제조 시설 안전 감시 (71679)

`object_information_human` 필드로 사람 객체 정보를 명시적으로 포함하고, 바운딩박스 라벨링이
확정되어 있습니다. 40만 장 규모에 일반 다운로드가 가능합니다.

**실내 산업 시설 환경이라 밀폐공간 탐색이라는 목표 도메인과 가장 가깝습니다.** 일반 CCTV와
열화상 CCTV를 함께 포함해 저조도 대응 검토에도 유리합니다.

- 장점: 도메인 적합성, 규모, 접근성, 열화상 포함
- 단점: 라벨 스키마 미확인, 다운로드 용량 미상(수백 GB 가능성)

### B — 1인칭 시점 보행영상 (159)

규모가 가장 크고 저작권 제약이 가장 느슨합니다. 다만 **1인칭 보행 시점(실외 보도 중심)** 이라
UGV 카메라 시점과는 유사하지만 재난·실내 환경과는 거리가 있습니다.

A가 막힐 경우의 대안, 또는 person 다양성 보강용 추가 데이터로 사용합니다.

### C — 지능형 관제 서비스 CCTV (71850)

안전사고 6종(침입, 싸움, **쓰러짐**, 군집, 인파밀집, 침수) 중 **쓰러짐 이벤트 영상이 45건(15%)**
포함되어 있습니다. 300건이라 학습에는 부족하지만 **검증 자산으로서 가치가 큽니다**(3절).

### D — 낙상사고 위험동작 (71641) — 사용 불가

내용만 보면 keypoint와 BBOX를 모두 갖춘 최적의 데이터셋입니다. 그러나 **보건의료 데이터로
안심존을 통해서만 개방되고 IRB 심의 결과 통지서가 필요합니다.** 안심존은 외부 반출이 차단된
격리 분석 환경이라 로컬 다운로드·학습이 불가능합니다.

> **내용이 좋다는 이유로 무리하게 시도하지 않습니다.** 1주 스프린트에서 IRB 심의를 통과할 수
> 없고, 통과하더라도 안심존 안에서는 이 프로젝트의 학습 파이프라인을 돌릴 수 없습니다.
> 다음 스프린트 이후 별도 절차로 검토합니다.

### E — 실내(편의점, 매장) 사람 이상행동 (71550) — 1순위

이상행동 8종(**전도**, 파손, 방화, 흡연, 유기, 절도, 폭행, 이동약자) 중 **전도(쓰러짐)가 807건**
확보되어 있습니다. C(45건)의 18배입니다.

**C와 D의 장점을 합치고 단점을 뺀 후보입니다.**

| | C (71850) | D (71641) | **E (71550)** |
|---|---|---|---|
| 쓰러짐 규모 | 45건 | 다수 | **807건** |
| bbox | ❌ | ✅ | **✅** |
| keypoint | ❌ | ✅ | **✅** |
| 접근성 | 일반 | ❌ 안심존·IRB | **일반** |
| 환경 | 실외 CCTV | 실험 촬영 | **실내 매장** |

- **bbox가 있어 파인튜닝에 쓸 수 있습니다.** C로는 불가능했던 부분입니다.
- **keypoint가 있어 임계값 보정이 가능합니다.** 정답 관절과 우리 Pose 추정을 직접 대조할 수
  있어, 3.1절에서 확인된 "관절을 못 쓰는 문제"를 정량화할 수 있습니다.
- 실내 환경이라 밀폐공간 탐색이라는 목표 도메인에 C보다 가깝습니다.

⚠️ **라벨이 XML입니다.** 다른 후보(JSON)와 parser가 다릅니다.
⚠️ **클래스 이름이 `쓰러짐`이 아니라 `전도`입니다.** 파일 목록에서 "쓰러짐"으로 찾으면
안 나옵니다.
⚠️ 매장 CCTV라 카메라가 높은 곳에 있습니다. UGV의 낮은 시점과는 여전히 다릅니다(3.1절 한계).

### F — 사람동작 영상 (aidata/138) — 보류

20만 클립·50여종에 2D keypoint(3D는 2만 클립)를 갖춘 대규모 자산입니다. 다만 **동작 인식용으로
연출 촬영일 가능성이 높고** bbox 포함 여부가 미확인입니다.

현재 병목은 Pose가 아니라 **Detect가 누운 사람을 못 잡는 것**이므로(3.1절), Pose 모델
파인튜닝이 필요해지는 시점까지 보류합니다.

## 3. 확보 순서 — 검증용을 먼저 받습니다

> **2026-08-04 개정** 이 절의 원래 계획은 C를 먼저 받는 것이었고, 실제로 받아 3.1절의 결과를
> 얻었습니다. 다만 **C에 bbox가 없어 파인튜닝 경로가 막혔고**, 같은 역할을 더 잘 하는
> **E(71550)**를 찾았습니다. 아래 "검증용을 먼저"라는 원칙 자체는 유효하며, 대상만 C → E로
> 바뀝니다. 최신 우선순위는 4절입니다.

**C(300건)를 A(40만 장)보다 먼저 확보합니다.** 규모 역순이지만 의도된 순서입니다.

### 근거

현재 파이프라인은 COCO 사전학습 `yolo26n`을 씁니다. 여기에 **검증되지 않은 전제**가 하나 있습니다.

> 바닥에 누운 사람을 사전학습 모델이 탐지하는가?

이것이 참이 아니면 `FALLEN` 판정(04 25.6) 자체가 성립하지 않습니다. Detect가 사람을
못 잡으면 Pose도 자세 판정도 실행되지 않기 때문입니다. 즉 **탐지 실패는 임계값 조정으로 해결되는
문제가 아니라 학습 데이터로만 해결되는 문제입니다.**

C의 쓰러짐 이벤트 45건은 이 질문에 답할 수 있는 **실제 현장 영상**입니다. 300건이라 다운로드가
가볍고, 학습 없이 바로 추론에 물려 확인할 수 있습니다.

### 이 확인이 이후 계획을 가릅니다

| 결과 | 의미 | 다음 |
|---|---|---|
| 누운 사람이 잡힌다 | 사전학습으로 최소 기능 성립 | A로 파인튜닝해 정확도 향상. 임계값 조정(ISSUE-06) 착수 가능 |
| 안 잡힌다 | **쓰러짐 탐지 기능이 현재 미성립** | A 파인튜닝이 선택이 아닌 필수. 비정형 자세 샘플 확보가 최우선 |

어느 쪽이든 A는 필요하므로, **A 신청은 C 확인을 기다리지 않고 병행합니다.** 승인·다운로드에
시간이 걸리기 때문입니다.

### 검증 절차

```bash
# C에서 쓰러짐 영상을 data/pose_test/에 배치한 뒤
python -m src.main --source data/pose_test/<쓰러짐영상>.mp4 \
  --frame-log --output runs/lying-check
```

`frames.jsonl`에서 순서대로 확인합니다. **앞 항목이 실패하면 뒤 항목은 의미가 없습니다.**

| # | 확인할 것 | 필드 | 실패 시 의미 |
|---|---|---|---|
| 1 | 누운 사람이 **탐지되는가** | `detection` 존재 여부 | 파인튜닝 없이는 기능 미성립 |
| 2 | 관절이 **잡히는가** | `pose`, `posture.signal_count` | 3~4면 관절 사용, 2면 형상·부동만 |
| 3 | **FALLEN으로 판정되는가** | `posture.status` | 임계값 조정 대상 |
| 4 | 점수가 문턱 근처인가 | `posture.fallen_score` | 0.5 부근이면 폭 조정 필요 |
| 5 | 어느 신호가 판정을 끄는가 | `posture.signals` | 가중치 조정 근거 |

### 이 데이터가 필요한 진짜 이유

개발 PC 실측(2026-08-03, 관측 27,556건)에서 `FALLEN` 비율이 22%로 나왔고, 분해해 보니
`score_vertical_extent`(FALLEN 평균 0.80)가 판정을 끌고 있었습니다. 임계값
`vertical_extent_ratio: 0.25`가 가림 상황에서 잘못 걸리는 것으로 보입니다.

| `vertical_extent_ratio` | FALLEN 비율 |
|---|---|
| 0.25 (현재) | 22% |
| 0.15 | 15% |
| 0.12 | 13% |

**그런데 이 데이터에는 실제 쓰러진 장면이 하나도 없어 값을 정할 수 없었습니다.** 전부 오탐이라
가정하고 조이면 진짜 쓰러진 사람도 못 잡는 설정이 됩니다. **어느 값을 어느 범위에서 고를지는
이미 나와 있고, 데이터만 있으면 됩니다.**

조정 대상은 임계값·가중치 7개입니다(`configs/pipeline.yaml`의 `posture` 블록).
`fallen_threshold`, `torso_horizontal_deg`, `bbox_aspect_ratio`, `vertical_extent_ratio`,
`weight_*` 3종. 최종적으로는 로지스틱 회귀로 교체할 자리입니다.

## 3.1 C(71850) 실측 결과 (2026-08-04)

Validation 쓰러짐 5클립(`E02_041`~`E02_045`)을 받아 현재 파이프라인에 그대로 물렸습니다.

### 라벨에 bbox가 없습니다

JSON이 클립당 약 700바이트이며 **클립 단위 메타데이터뿐입니다.**

```json
{"metadata": {"file_name","width","height","frame_count","night"},
 "annotations": {"event_class":"Falldown", "event_frame":[[1840,2323]],
                 "event_length", "event_caption", "depersonalization"}}
```

**5절의 미확인 항목 "C의 bbox 포함 여부"에 대한 답은 "없음"입니다.** 따라서 **C는 학습에
쓸 수 없습니다.** 다만 `event_frame`이 정답 구간을 주므로 **대조 검증에는 쓸 수 있습니다.**

### 쓰러지는 순간 탐지가 무너집니다 (E02_041, 주간, 3,600프레임)

같은 영상 안에서 구간만 나눠 비교했습니다. 카메라·거리·조명이 통제된 대조입니다.

| 구간 | 탐지율 | 프레임당 인원 | 최고 `fallen_score` |
|---|---|---|---|
| 이벤트 전 (0~1839) | **99.3%** | 2.07 | 0.750 |
| **이벤트 (1840~2323)** | **32.6%** | **0.34** | **0.318** |
| 이후 (2324~3599) | 67.4% | 1.19 | 0.561 |

- **`FALLEN` 판정 0건.** 3,600프레임 내내 한 번도 문턱(0.5)을 넘지 못했습니다.
- **점수가 정답과 반대로 움직입니다.** 최고 점수가 나온 곳은 쓰러지기 **전**(0.750)이고,
  정작 쓰러진 구간은 0.318로 문턱 미달, 중앙값 0.052입니다.
- 원인은 임계값이 아닙니다. **쓰러진 사람이 탐지되지 않아 점수를 매길 대상 자체가 없습니다.**
- bbox 폭 중앙값 **52px**, Pose 최소 크기(80×80) 충족 **20.3%**,
  이벤트 구간 `signal_count` 중앙값 **2**(= 관절 없이 형상·부동만).

### 이 결과의 한계 — "안 된다"를 증명하지는 못합니다

E02_041의 캡션은 **"세 사람이 동시에 뒤엉켜 쓰러짐"**입니다. 탐지 실패의 원인이
① 누워서인지 ② 서로 가려서인지 ③ 너무 작아서인지 **분리되지 않습니다.**

이 데이터는 답이 비대칭입니다.

| 결과 | 해석 |
|---|---|
| 탐지된다 | **강한 긍정.** 최악 조건에서 잡혔다면 UGV 근거리는 더 쉽습니다 |
| 안 잡힌다 | **결론 못 냄.** 자세·가림·크기가 교란돼 있습니다 |

### 결론

**증거는 "파인튜닝 필수" 쪽으로 기울었지만 확정은 아닙니다.** 그리고 C로는 파인튜닝을 할 수
없으므로(bbox 없음), **bbox·keypoint를 갖춘 E(71550)가 필요합니다.**

임계값 보정도 C로는 불가능합니다. bbox 폭 52px에서는 Pose가 거의 실행되지 않아
`torso_angle`·`vertical_extent_ratio`를 계산할 수 없습니다. 문턱을 낮춰 억지로 돌리면
**부정확한 keypoint로 임계값을 정하는 셈**이라 의미가 없습니다.

> **도메인 한계는 E에도 남습니다.** C는 실외 CCTV, E는 매장 CCTV로 둘 다 카메라가 높습니다.
> UGV는 바닥에서 수십 cm 높이로 올려다봅니다. 누운 사람의 실루엣은 각도에 크게 달라지므로,
> **CCTV에서 맞춘 임계값이 UGV에서 맞는다는 보장이 없습니다.** 최종 보정에는 우리 시점의
> 영상이 필요하며, 이는 직접 촬영으로만 얻을 수 있습니다(§28.1 ISSUE 2b).

> **라벨 파일(수 KB)을 먼저 받아 열어보면 몇 초에 끝났을 일입니다.**

### 다운로드 순서 (E 기준)

AI-Hub는 대체로 아래 구조입니다. **클래스 이름이 `쓰러짐`이 아니라 `전도`입니다.**

```text
Training/   ├─ 01.원천데이터    TS_전도.zip   ← 영상
            └─ 02.라벨링데이터  TL_전도.zip   ← XML
Validation/ ├─ 01.원천데이터    VS_전도.zip
            └─ 02.라벨링데이터  VL_전도.zip
```

1. **`VL_전도`(라벨) 먼저** — 수 KB. XML을 열어 bbox·keypoint 구조를 확인한다
2. 구조가 맞으면 `VS_전도`(영상)로 파이프라인 대조
3. 파인튜닝 단계에서 `TS_전도` / `TL_전도`

**전도 외 7종(파손·방화·흡연·유기·절도·폭행·이동약자)은 받지 않습니다.**

## 6. class map

이번 스프린트는 person 단일 클래스입니다. 다음 스프린트의 클래스 추가에 대비해 **id가 아니라

```python
CLASS_MAP = {
    "person": 0,
    # 다음 스프린트 이월 — 데이터 확보 후 추가
    # "fire_extinguisher": 1,
    # "exit": 2,
    # "danger_sign": 3,

```

`requirements.md`의 초안에 있던 `Fire Extinguisher` / `Exit` / `Danger Sign` 3종은 폐기가 아니라
**다음 스프린트로 이월**입니다. 클래스 추가는 데이터 확보·라벨링·재학습을 모두 수반하므로
